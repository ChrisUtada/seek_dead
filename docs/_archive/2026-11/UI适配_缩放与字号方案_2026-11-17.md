# Seek Dead · UI 适配方案：缩放、黑边与字号（2026-11-17）

> 本文只做诊断与方案，不改代码、不改场景、不改任何 `.tres` 数值。
> 依据：`project.godot` 实测值（用 Godot headless 逐项读取，非推断）、`autoload/window_policy.gd`、`scripts/ui/battle_hud.gd`、`scripts/ui/type_scale.gd`、Godot 官方《Multiple resolutions》文档、各素材原始许可证文件。

---

## 0. 结论先行

现在的"UI 适配问题"其实是**三个独立问题**被当成一个问题在解，而它们的解法互相冲突：

| # | 问题 | 真正的成因 | 唯一有效解法 | 副作用 |
|---|---|---|---|---|
| 1 | 像素大小不均匀、边缘发毛 | `scale_mode=fractional`：1 逻辑像素被摊成 2 或 3 个物理像素 | `scale_mode=integer` | **必然出现黑边**（引擎硬约束） |
| 2 | 非 16:9 窗口有黑边 | `stretch/aspect=keep`（默认值，项目里根本没写） | 改 `expand` | 所有贴边 UI 会跑位，必须先锚点化 |
| 3 | 中文 9–10px 发虚，"像换了字体" | 字体原生 12px，却按 10px / 16px 渲染 → 每级缩放都是 0.83× / 1.33× 非整数 | 换成 **10px 原生**字体，只允许 10 / 20 | 字宽变了，163 条排版断言要重标定 |

**关键认知**：问题 3 与窗口缩放**无关**。哪怕窗口给到完美的 4×，`font_size=10` 配 12px 原生字模仍然是 20/12 的非整数缩放，一样虚。字号必须等于字模原生像素尺寸或它的整数倍——这条在现在的 `TypeScale` 里全线违反（9 / 10 / 16 全部不是 12 的整数倍）。

**推荐（零美术迁移、零布局改动）**：
保持 480×270 → 打开 `integer` → 去掉 960×540 上限并按屏幕选最大整数倍 → 窗口尺寸吸附整数倍 → 字号换 10px 原生字体、阶梯收敛到 10/20。
结果是：**1080p / 4K 全屏零黑边且像素完美，窗口模式永远零黑边**；720p / 1440p / 16:10 全屏留边（这时用掌机外框把边做成设计）。

### 1.1 与 `window_policy.gd` 的判断冲突

`autoload/window_policy.gd` 第 5 行写的是「**永不出现黑边**，宁可非整数缩放时画面轻微不均匀」，第 9 行写「不用 `scale_mode="integer"`，那会在非整数尺寸留黑边」。

但 `aspect` 是 `keep`——`keep` 的定义就是"视口保持原尺寸，多余部分补黑边"。只要窗口不是严格 16:9，就一定有黑边，跟 `scale_mode` 选什么无关。所以现在的实际状态是**同时有黑边和非整数像素**，两种代价都付了，一个好处都没拿到。

两条常见做法在引擎里是互斥的：

- `integer` → 像素均匀，**四周补黑条**（官方原文）；
- `fractional` → 铺满窗口，**像素宽窄不一**。

不存在"既整数又无黑边"的开关。要不留边，只能让**画布跟着窗口变**（`expand`），代价是布局必须锚点化。

### 1.2 分辨率阶梯：480×270 只在 1080p / 4K 上干净

`scale = floor(min(W/480, H/270))`，余量即黑边：

| 屏幕 | 480×270 基准 | 黑边 |
|---|---|---|
| 1280×720 | 2× → 960×540 | 320×180 |
| 1366×768 | 2× → 960×540 | 406×228 |
| 1600×900 | 3× → 1440×810 | 160×90 |
| **1920×1080** | **4× → 1920×1080** | **0** |
| 2560×1440 | 5× → 2400×1350 | 160×90 |
| **3840×2160** | **8× → 3840×2160** | **0** |

对照 640×360 基准（官方文档点名推荐它，理由正是这条）：720p / 1080p / 1440p / 4K 全整数无黑边，只有 1366×768 和 1600×900 会留边。

**这是"完美适配"无法回避的取舍**：480×270 是美术定的（48px 小人 = 屏宽 10%，字号 9–13px），640×360 是显示器阶梯定的。换基准的代价见 §2.2，不建议现在动。

### 1.3 窗口策略自身的三个硬伤

1. **上限锁死在 960×540**：`window_policy.gd` 调 `window_set_max_size(960, 540)`。玩家在 1080p 屏幕上只能看 1/4 面积，3× / 4× 两档直接被关掉。
2. **没有全屏入口**：`project.godot` 的 `[input]` 里没有 fullscreen 动作，也没有代码调 `window_set_mode`。也就是说玩家现在只能看窗口，永远进不了全屏——"1080p 4× 零黑边且像素完美"这个唯一成立的组合，实际用不上。
3. **窗口尺寸不吸附**：用户可以拖到 900×580 这种任意尺寸，`keep` 立刻补边、`fractional` 立刻出混合像素宽。

### 1.4 字号：三层非整数缩放叠在一起

`assets/fonts/VonwaonBitmap-12px.tres` 是**内嵌字模位图**（`FontFile` + `sub_resource Image`），原生 12px，`subpixel_positioning=0`，`font_name="VonwaonBitmap 12px"`。而 `TypeScale` 的阶梯是：

| 常量 | 值 | 与原生 12 的关系 | 结果 |
|---|---|---|---|
| SYMBOL | 16 | 1.33× | 上采样，笔画错位 |
| REEL / OVERLAY / TITLE / LEAD / SUBTITLE / BODY | 10 | 0.83× | 下采样，笔画粘连 |
| MEDIUM / META / TINY / CAPTION | 9 | 0.75× | 下采样更严重 |

再叠上窗口的 2× / 3× / 4×，最终是 `(10/12) × 2` 这种乘积——两层都不是整数。`type_scale.gd` 注释里"9-11px 仍清晰"的结论，与 12px 位图字模的实际行为不符。

### 1.5 布局：底栏是绝对坐标，`expand` 一开就错位

`scripts/ui/battle_hud.gd:2724 _layout_bottom_zones()` 里写的全是屏幕绝对坐标：

- `spin_bar.position = Vector2(190, 252)`、`size = Vector2(100, 18)`
- `GoldIcon.position = Vector2(444, 211)`、`GoldLabel.position = Vector2(456, 211)`
- 四区 X 段：武器+技能 20~178 / 转轮 180~298 / 腰带 300~426 / 金币 428~458

并且 `_process()` 每帧重摆（`battle_hud.gd:2757`）。只要画布宽度从 480 变成 533（1600×900 @3× + expand），金币框就会停在 x=456，右侧空出一块。**所以 `expand` 之前必须先做锚点化，顺序不能反。**

## 2. 方案对比

### 2.1 方案 A：480×270 + integer + 窗口吸附（推荐）

- `stretch/mode = canvas_items`（保留，文字按窗口分辨率重绘，这一点对文字有利）
- `stretch/scale_mode = integer`
- `stretch/aspect = keep`（保留）
- 去掉 `window_set_max_size`，改为**启动时按屏幕可用区选最大整数倍**，并把窗口尺寸吸附到 `480×270` 的整数倍
- 全屏：取屏幕能容纳的最大整数倍；1080p / 4K 恰好整除，零黑边
- 必要时用 `DeviceFrame` 的视觉语言把非目标分辨率的留边画成掌机外框（把"意外黑边"变成"设计边框"）

| | |
|---|---|
| 收益 | 100% 像素均匀；窗口模式永远零黑边；1080p / 4K 全屏零黑边；布局零改动；美术零改动 |
| 代价 | 720p / 1440p / 16:10 全屏留边；需接受"游戏不是铺满屏幕"的观感 |
| 工作量 | `window_policy.gd` 重写 + 一个输入动作 + 一个分辨率设置项。约 60 行，1 次提交 |

### 2.2 方案 B：换基准到 640×360

| | |
|---|---|
| 收益 | 720p / 1080p / 1440p / 4K 全整数零黑边（官方推荐它的唯一理由） |
| 代价 | `scenes/ui/*.tscn` 约 135 处几何 + UI 脚本约 135 处 `Vector2` 字面值全部 ×1.33（≈270 处）；48px 小人从屏宽 10% 掉到 7.5%，要维持观感得把立绘重画到 64px；字号需同比 +33%（10→13，仍非原生） |
| 结论 | **不建议**。它把"适配"问题换成"美术重制"问题，且 13px 依然不满足原生字号规则 |

### 2.3 方案 C：integer + expand（无黑边 + 像素均匀，但不完美）

- 视口尺寸变成 `窗口 / floor(scale)`，例如 1600×900 @3× → 533.33×300。**逻辑画布出现小数**，1px 线框会时而 3px 时而 4px；需要同时开 `rendering/2d/snap/snap_2d_transforms_to_pixel` 才能压住。
- 前置条件：底栏四区锚点化 + `ReelPanel`（现 `160..314` 写死）居中化 + 163 条排版断言在 480/533/640 三种宽度下都过。
- 结论：能做出"任何分辨率都不留边"，但它是**用 1px 线框的稳定性换**的。像素风项目里这笔账一般不划算。

### 2.4 方案 D：世界层 / UI 层分离（真正彻底的解法）

- 世界：480×270 `SubViewport`，整数倍放大居中；
- 底与外框：原生分辨率铺满，黑边区域被背景吃掉；
- UI：原生分辨率重绘，按锚点布局，字号按物理像素给（1080p 下 20 / 30px）。

这是"任意分辨率无黑边 + 文字永远锐利 + 像素均匀"三者同时成立的唯一架构，代价是 HUD 要从 480 画布搬到原生层（`battle_hud` 全部坐标重写）。

**建议作为长期演进，不作为本轮动作。**

## 3. 推荐执行路线（一次只改一项）

> 你们 2026-11-17 10:20 的教训写得很清楚：四项叠加导致画质连续两次恶化且无法归因。以下每步都可独立回退、独立验收。

### Step 0 · 基线（不改任何东西）

用 `tools/shoot.gd` 出 6 张图存档到 `docs/baseline/2026-11-17_ui_scale_before/`：

960×540 窗口 / 1280×720 窗口 / 1366×768 窗口 / 1600×900 窗口 / 1920×1080 全屏 / 一个 16:10 尺寸（如 1440×900）。

验收：能一眼看出后三张有黑边、且像素列宽不均匀。

### Step 1 · 窗口策略（只动 `window_policy.gd` + 一个输入动作）

1. 删掉 `window_set_max_size`；
2. 启动时：`scale = clamp(floor(min(screen_w/480, screen_h/270)) - 1, 1, 8)`，窗口设为 `480*scale × 270*scale`，居中；
3. `size_changed` 时把窗口尺寸吸附到最近的整数倍（容差 ±8px，避免抖动）；
4. 新增 `toggle_fullscreen` 输入（F11），调用 `DisplayServer.window_set_mode(WINDOW_MODE_FULLSCREEN)`；全屏时按 §2.1 选最大整数倍；
5. `project.godot` 加 `stretch/scale_mode="integer"`。

验收：

- 1080p 全屏截图与 960×540 窗口截图**逐像素等比**（4× 与 2× 的像素块形状一致）；
- 任意拖拽后窗口内不出现黑边；
- `run_smoke.bat` 全绿。

### Step 2 · 字号（只动字体资产 + `type_scale.gd`）

1. 引入 Fusion Pixel 10px（OFL 1.1，详见 §4），保留 12px 版做备选；
2. `TypeScale` 收敛为 `10`（正文全部）与 `20`（强调/标题），`SYMBOL` 从 16 改 20 或直接用 10——**必须实测 20px 在 42px 转轮格内是否溢出**；
3. 跑 `tests/g8_screens_layout_test.tscn`（163 条）与 `g8_layout_test`（147 条），修溢出；
4. 逐级截图确认 10 → 20 → 30 → 40 物理像素都是整数倍。

> 注意：换字体会改字宽，所有换行点都会变。这是"必须成批重标定"的一步，不能和 Step 1 同批。

### Step 3 ·（可选）底栏锚点化

把 `_layout_bottom_zones()` 的四区从绝对坐标改为「左右两区锚左右边、金币锚右下角、转轮居中」。这一小步在 480 宽度下**视觉零变化**（可用现有断言证明），但它是 Step 4 的前置。

### Step 4 ·（可选）`expand` 或双层架构

只有在 Step 3 完成、且你确认要"跨所有分辨率都不留边"时才做。

### 4.2 实测：Zpix 在当前文案里一次都没用上，但它仍然随包分发

字体链路（`assets/fonts/VonwaonBitmap-12px.tres:24`）：

```gdscript
fallbacks = Array[Font]([ExtResource("1_zpix")])
```

即 **主字体 = VonwaonBitmap（凤凰点阵体 12px），Zpix 只是兜底**。兜底是否真的被调用，取决于主字缺不缺字。实测：

```
PROBE|primary=VonwaonBitmap 12px
PROBE|fallback=Zpix
PROBE|corpus_chars=1434196  unique_above_U2E00=1621  missing_in_primary=98
PROBE|missing_sample=💰🗂🧪🚫🔍🛡🔥🩸🔒🪨💥💢🔋🌫🪢🪓🔴📈🛒…（全是 emoji）
PROBE|missing_in_zpix=98
```

扫描 `scripts/` `scenes/` `resources/` `autoload/` 全部 `.gd/.tscn/.tres` 文本后：

- 1610 个汉字/符号由 VonwaonBitmap 渲染（它的 GB2312 6763 字覆盖了当前全部中文）；
- 主字缺的 98 个**全是 emoji**，而 Zpix 同样缺这 98 个 → **Zpix 对汉字的实际贡献是 0**。

三点不能因此掉以轻心：

1. **它仍然被打进包里**。`export_presets.cfg` 两个预设都是 `export_filter="all_resources"`、`exclude_filter` 为空或只排除 `tests/*, tools/*`；而且 `.tres` 的 `fallbacks` 会强制把它作为依赖收进去。**"没用上"和"没分发"是两件事**，Zpix 的授权管的正是分发与嵌入。
2. **它仍是活跃路径**。只要出现主字没有的字——生僻字、繁体、玩家自定义名、未来多语言——Zpix 立刻开始渲染，风险从"理论"变成"每帧"。
3. **删它之前要先补位**。直接移除 fallback 会让那 98 个 emoji 失去字体，掉到系统 emoji 或豆腐块。正确做法是换成 OFL 字体（Fusion Pixel）再移除 Zpix，两步同批但同批验收。

复现方式（只读，不改项目）：

```
Godot_v4.7-stable_win64_console.exe --headless --path . --script res://.workbuddy/tmp/probe_font.gd
```

## 5. 验收标准（可直接写进 `run_smoke.bat` 或人工清单）

1. **像素一致性**：480×270 下画一条 1px 竖线，在 2× / 3× / 4× 窗口里量到的物理宽度必须分别是 2 / 3 / 4，且整屏只出现这一种宽度。
2. **黑边**：1080p 全屏、4K 全屏、960×540 窗口三种情况为 0；720p / 1440p 全屏允许留边，但必须左右与上下对称。
3. **字号**：所有 `font_size` ∈ {10, 20}，且等于字体原生尺寸的整数倍；截图放大 4× 后笔画无灰边、无粘连。
4. **排版**：`g8_screens_layout_test` 163/163、`g8_layout_test` 147/147、`run_smoke` 全绿。
5. **回归**：同一随机种子下战斗结果不变（换字体/换窗口不得影响逻辑）。
