## 2. 最终架构（代码事实）

### 2.1 模块与职责

| 模块 | 职责 |
|---|---|
| `RewardDefinition` / `RunSnapshot` / `DraftResult` | 纯数据类 |
| `RewardRegistry` | 扫描 `resources/rewards/defs/`，校验卡定义 |
| `RunStateAnalyzer` | 从武器/符号/已获奖励推导 BuildState 标签（五元素） |
| `RewardEvaluator` | 六项评分，**仅用于 debug 展示，不参与抽样** |
| `DraftComposer` | 硬过滤 + 采样 + 组合选择 + 兜底，持有专用 RNG |
| `RewardResolver` | 把 effect_id 分发到现有结算接口，不复制战斗逻辑 |
| `RewardPresentation` | DraftResult → UI view，字段兼容 `card_factory` |
| `run_telemetry` | 5+2 个 Draft 事件，含局末构筑 vs 结果 |

### 2.2 采样模型（★ 核心，今天的重构重点）

```
候选池 → 硬过滤(validate/eligibility_rule/满血治疗)
       → 按稀有度加权无放回抽(count)  ← 出现率只由 RARITY_WEIGHT 决定
       → 同标签软惩罚(DIVERSITY_FACTOR=0.65)保多样性
       → 组合评分(稀有度梯度张力 + 协同 + 相似度惩罚 + 随机)
       → 采样6组带权选一组(非唯一Top1)
       → 兜底(永不空屏、不塞假卡)
```

- `RARITY_WEIGHT = {common:60, uncommon:30, rare:9, epic:1}`
- 情境评分已**降级为信息性**：只在 `compose(debug=true)` 时计算，供 `explain_last()` 展示

## 3. 设计决策记录（今天的变更链）

### 3.1 删除「幸运余波」（`4807ede`）
- 原为第 5 张验证卡（免费重抽），删除后卡池 5→4
- 理由：免费重抽不产生构筑价值，违背「三选一是构筑决策引擎」定位；
  战斗内重转已有 3 张消耗品（重转卷轴/赦免令/重铸风暴），功能重复
- 连带清理：`free_reroll`/`grant_consumable` 分支、Composer 免费重抽状态、Presentation 文案

### 3.2 火焰共鸣文案修正（`4807ede`）
- 原："已有火系武器/符号/技艺时产生协同"——承诺玩家感知不到的战斗收益
- 新："本局火焰构筑 +1：让火系装备/符号/牌谱更容易在后续三选一中出现"
- 定性：它是**抽卡加权卡**（构筑导向），不是战斗增益卡。不是削弱，是消除误导

### 3.3 解耦采样（`253b623`）——今天最重要的重构
- **问题**：`rarity`/`base_weight` 原是死字段，采样权重 100% 来自情境评分。
  导致 rare 不 rare（火焰 rare 27.5% ≈ 战场 common 28%）、低血必出回血（系统替玩家决策）
- **改法**：稀有度接管出现率；情境评分降级为仅 debug 信息性展示；保留硬过滤与多样性
- **依据**：经典 roguelike 最佳实践（Slay the Spire / Balatro）——稀有度定概率，玩家定价值

### 3.4 补四元素对称卡（`253b623`）
- 冰霜/剧毒/圣辉/虚空共鸣，复用 Resolver 已有的 `params.element` 支持，零代码
- 卡池 4→8，否则 4 选 3 时任何权重都失效

### 3.5 共鸣卡品质统一（`253b623` 后的修正，未单独提交）
- 用户 F6 发现：同系列共鸣卡品质不一（冰霜普通/火焰稀有）
- 修复：5 张共鸣卡统一为 rare

### 3.6 epic 档刻意留空
- 四级体系（common/uncommon/rare/epic）容器完整：权重表/显示名/颜色都齐全
- 但**没有配得上"传说"的卡**：epic 的经典定义是"开创玩法"，不是"数值更大"
- "强化共鸣 +2" 会被用户否掉（同系列换数字标高档 = 刚修正的错误）
- 结论：留空是诚实且符合经典做法的选择。等想清楚牌谱解锁，那是天然 epic

### 3.7 重复获得：当前设计允许无限重复
- `stack_rule`/`max_stack` 又是定义了未实现的字段——采样层不读取
- 对现有 8 张卡（全是"可叠加成长"型）无限重复是**正确的**
- 等做签名解锁这类"一次性卡"时，才需实现：加已获 id 集合 + `_eligible()` 按 max_stack 过滤

## 4. 踩坑教训（供后续避坑）

| # | 教训 | 出处 |
|---|---|---|
| 1 | **品质是给玩家看的语义，不是给统计用的旋钮**。同系列同效果卡必须同品质 | §3.5 返工 |
| 2 | **先核清术语再做方案**。我曾把"三选一免费重抽"和"战斗内转轮重转"混为一谈 | §3.1 讨论 |
| 3 | **定义了 ≠ 实现了**。`rarity`/`base_weight`/`stack_rule`/`max_stack` 都曾是死字段 | §3.3 / §3.7 |
| 4 | **Godot 4.7 对无类型 `:=` 推断频繁失败**。右侧是 Variant/成员/条件表达式/字面量索引时一律显式标类型 | 全程多次 |
| 5 | **String 用 `is_empty()`，不是 `empty()`** | P1 阶段 |
| 6 | 战斗演出不得消耗全局 RNG（项目铁律 10） | 架构约束 |
