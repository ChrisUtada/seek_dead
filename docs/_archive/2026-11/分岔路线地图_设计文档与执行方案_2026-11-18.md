> 日期：2026-11-18
> 性质：设计文档 + 执行方案（**未改代码**）
> 目标：把现有 14×9 开放网格棋盘（自由移动 + 巡逻怪 + 陷阱）替换为杀戮尖塔式分岔路线图
> 依据：对 `scripts/board/` 全部 12 个文件 + controller / room_flow 的深度核查（见 §2）
> 配套：与三选一重构的关系见 `战后三选一重构_最终状态与决策记录_2026-11-18.md`

## 1. 结论先行

**方向正确：分岔路线图是经典 roguelike 的最佳实践，比开放网格更适合本项目。**

- 开放网格的"自由探索"与核心玩法（转轮战斗）无关，反而用巡逻 / 陷阱 / 回合分散注意力——正是"喧宾夺主"
- 分岔图的价值是**路线取舍**（战斗 / 精英 / 商店 / 休整 / 事件），地图本身零玩法，重心回到战斗
- 项目已有完整的"节点内容层"，**改动可收敛在 `scripts/board/` 内**，战斗与三选一系统零改动

### 1.1 先纠正三个认知偏差（核查发现）

动工前必须澄清，否则方案会建立在错误前提上：

1. **骰子机制早已不存在。** 2026-11-14 "单路径收敛"时 `dice_sides` 等字段已物理删除，
   `board_system.gd` 里的 `dice / last_roll / can_roll() / roll_dice()` 全是返回 0/false 的空桩。
   真正"喧宾夺主"的是 **14×9 网格四邻自由移动 + 巡逻怪追逐 + 破甲陷阱 + 原地等待推回合**。
2. **当前不是"分岔路线图"，是"开放网格自由探索"。** 玩家可在 126 格内任意四邻走动、回访、等待。
   这与杀戮尖塔"只能沿连线选下一层节点、不可回头"的拓扑完全不同。
3. **项目已在 node_mode 棋盘模式上**（只是 `board_config.enabled=false` 默认走线性）。
   所以任务是"**现有网格棋盘 → 分岔路线棋盘**"，不是"线性 → 地图"。

## 3. 分岔路线图设计

### 3.1 拓扑模型：DAG 分层图

```
层0  起点
      │
层1  战斗 ─┬─ 精英
           └─ 宝箱
      │         │
层2  商店 ─┬─ 事件 ─┬─ 休整
           │        │
层3  战斗 ─┴────────┴─ 精英
      │
层4  BOSS（汇聚）
```

规则：

- 每幕 7 层（起点 + 5 中间层 + BOSS），每层 2-3 个候选
- 连线只连相邻层（`layer → layer+1`），形成有向无环图（DAG）
- 玩家从当前层节点沿连线选下一层的 1 个；路径汇聚到该幕 BOSS
- **不可回头、不可回访**——这是与开放网格的本质区别
- 路线可判定：任意起点到 BOSS 都有通路（迁移 `map_grid.validate` 的思想）

### 3.2 节点类型与取舍

沿用现有 8 种类型，按经典风险收益配置：

| 类型 | 定位 | 出现层 |
|---|---|---|
| battle | 基础战斗，稳定收益 | 各层 |
| elite | 高风险高回报（好装备 / 铁砧点） | 中后层 |
| shop | 花钱买确定性 | 中后层 |
| rest | 回血 | 中后层 |
| chest | 免费物品 | 前中层 |
| armory | 武器二选一 | 前中层 |
| event | 随机神龛（heal / maxhp / ward） | 各层 |
| boss | 幕底汇聚 | 最后一层 |

**路线选择必须有取舍**——走精英拿好奖励但风险高，走商店花钱但安全，走休整回血但少收益。这是分岔图的全部价值。

### 3.3 BOSS 安排：4 选 1 随机，进幕即公开（★ 关键决策）

**现有机制**：每幕 4 个 BOSS 候选（如 act1：fixed 1 / rotating 2 / hidden 1），
由 `run_setup.gd:59 pick_boss()` 按 `boss_role` 权重随机抽 1 个。
这套机制在房间池层，与地图拓扑无关，**分岔图零改动复用**。

**决策（用户 2026-11-18 拍板）**：BOSS 随机 4 选 1 不变，但**结果在生成分岔图时就定好，
并在地图上提前显示**——玩家选路前就知道本幕 BOSS 是谁、什么元素、什么特性。

**为什么必须可见（系统性理由，非体验优化）**：

- 三选一的共鸣卡是"构筑导向卡"（提前下注元素），战斗又有元素克制环（×1.5 / ×0.85）
- BOSS 隐藏 → 玩家元素下注变盲赌 → 共鸣卡从"策略选择"退化成"抽奖"
- **BOSS 可见 = 构筑有靶子，这是共鸣卡系统成立的前提**
- 杀戮尖塔式做法（进 act 就公开 boss），不是"剧透"

**否决"4 个 BOSS 全摆上让玩家选"**：玩家会挑最弱的打，挑战被消解；且"选 boss"只有一个最优解，不是好取舍。

**落地影响**：

- 阶段 A：生成分岔图时对 boss 节点调 `pick_boss(candidates)` 定死 room（复用 `_assign_rooms`）
- 阶段 C：地图 BOSS 节点 + 顶栏显示 boss 名称 / 元素 / 特性（`_refresh_info` 扩展）

### 3.4 平衡性：已知 BOSS 会不会被"秒"（核查结论）

**担忧**：知道 BOSS 后针对性堆元素，是否一下打过去？——**基本不会**，四重约束：

1. **HP 量级远大于克制收益**：act1 BOSS HP 198–240、护甲 8–45；玩家基础 HP 100、基础武器伤害个位数到十几。
   ×1.5 是温和增益，绝无可能秒杀（需 20 倍以上增益）。
2. **克制是双向的**：火克冰 / 毒 ×1.5，但**冰克火**（`BEATS.ice=["fire"]`）。堆火打冰 boss 后，
   遇冰系敌人反被克——针对性构筑有代价，不是纯赚。
3. **护甲削弱纯元素爆发**：冰封铁瓮 20 甲、茧居石雕 45 甲，破甲需求天然限制元素堆叠。
4. **资源有限**：每层只能选 1 节点，金币 / 装备槽 / 三选一次数有限，玩家不可能堆满所有元素，只能专注一个方向——这本身就是取舍。

**原设计早有正反馈铺垫**：`frozen_urn`（冰 boss）的 `boss_reward_weapons` 前 3 把全是火系
（cinder_cleaver / fire_sword / flame_staff）——说明"针对性堆火打冰 boss"本就是预期玩法，不是漏洞。

**应对极端情况的手段**（若实测某元素 boss 被秒）：调该 boss 的护甲 / HP，或强化其 gimmick（如冰封铁瓮的"叠甲冻结列 + 蓄势爆发"），而**不是**削弱克制系统或隐藏 boss。

### 3.5 与转轮战斗的衔接

```
玩家选节点 → board.advance_to(id) → 沿边前进到下一层
  → 战斗节点：controller._on_board_node_entered → start_room_data → 转轮战斗
  → 胜利 → room_flow 战利品三选一 → _after_victory → board.return_to_board() → 回到分岔图
  → 非战斗节点：直接 _board_shop / _board_rest / ... 结算 → 回分岔图
  → 到达 BOSS → 胜利 → advance_act() → 生成下一幕分岔图
```

这段流程全部复用现有 controller / room_flow，**零改动**。

### 3.6 跨幕

- `advance_act()` 保留（它只调 `board.generate(config, next_act)`）
- 每幕生成一张新的分岔图，三幕结构不变
- `act_summaries` / `act_label()` 保留
- 最后一幕 BOSS 强制 `final_boss`（勇者的阴影），现有逻辑不变

## 5. 执行方案（分阶段）

> 原则：每阶段单独可验证、单独提交，不一次性推倒。

### 阶段 A：数据层 — 新建分岔图生成器（不动 UI）

- **新建** `scripts/board/branch_map_builder.gd`：生成 DAG 分层图（层 × 候选 + 连线），输出节点字典
- **改造** `map_board_builder.gd`：把 `MAP_GRID.generate + neighbors` 换成调 branch builder；保留 `_assign_rooms` 和 `fill_explore_fields`
- **BOSS**：在生成时对 boss 节点调 `pick_boss()` 定死 room（§3.3）
- **复用** `map_node_types.gd` / `map_reward.gd` / `map_progress.gd`（零改）
- **废弃** `map_grid.gd` / `map_patrol.gd` / `map_trap.gd`（先留在磁盘但不再引用，确认稳定后删）
- **验收**：headless 测试——每幕图满足"层间连通、BOSS 唯一且已定、类型分布合理、节点内容非空"

### 阶段 B：运行时 — 选边推进状态机

- **改造** `map_runtime.gd`：删坐标 / 回合 / 巡逻 / 陷阱 / 镜头，改为 `current_id` + 下一层候选集合 + `advance_to(id)` 沿边推进
- **改造** `board_system.gd`：保留门面 API，内部改调新 runtime；`legal_targets()` 返回下一层候选；`route_length()` 改实际路径长度；删骰子空桩
- **验收**：headless 测试——从起点沿合法边能走到 BOSS，不能跨层 / 不能回头，`current_id` / `consumed` 正确

### 阶段 C：UI — 分岔路线图渲染

- **改造** `board_screen.gd`：
  - 删 `MAP_RECT / CELL / COLS / ROWS`、棋子 + tween、四邻判定、巡逻 / 陷阱绘制
  - 新渲染：层 × 候选节点 + 连线（Line2D 或 `_draw`），当前节点高亮，可选节点可点击
  - 顶栏显示本幕 BOSS 名称 / 元素 / 特性（§3.3）
  - 保留：战斗确认层 `_show_battle_confirm`、收益文本 helpers、构筑 / 撤回面板、右栏信息
- **验收**：F6 目视——地图是分岔图不是网格，BOSS 信息可见，点击只走下一层，确认层正常

### 阶段 D：端到端与清理

- 全链路 F6：三幕走通、路线取舍有效、战斗 / 商店 / 休整 / 事件 / 宝箱都能到达并结算、BOSS 针对性构筑可行
- 更新 `board_config.tres`（删骰子残留注释，加"层数 / 每层候选数"参数）
- 更新过时工具 / 测试（`tools/g*_board_capture.gd` 里的 dice 写入、`tests/board_ui_test.gd` 等）
- 清理阶段 A 留下的废弃文件
- 回归：全项目 headless 测试 + 编辑器解析

## 6. 风险控制

1. **接口契约是生命线**：阶段 A/B 绝不能改 `board.*` 对外 API，否则 controller 要连锁改。每阶段用契约测试守住。
2. **内容层零改动**：`map_node_types / reward / progress` 三个文件本方案承诺不动，若发现必须改说明契约设计有问题，停下来重议。
3. **不要顺手加玩法**：本次只换地图拓扑，不加新节点类型、不改战斗、不碰刚完成的三选一系统。
4. **480×270 约束**：分岔图每幕 7 层 × 2-3 节点，要放大到易点击，别照搬 14×9 的 16.6px 格子。

## 7. 决策状态

### 已拍板（2026-11-18）

| 项 | 决策 |
|---|---|
| 地图形态 | 分岔路线图（DAG），替代开放网格 |
| BOSS 可见性 | 4 选 1 随机，生成时定死，地图上提前显示（§3.3） |
| BOSS 候选数 | 维持每幕 4 个，不摆上地图让玩家选 |
| 平衡点 | 不隐藏 boss，用 gimmick / 护甲调极端情况（§3.4） |

### 待拍板（动阶段 A 前确认）

1. **每幕层数**：建议 7 层（起点 + 5 中间层 + BOSS），每层 2-3 节点。太少没取舍，太多屏幕放不下。
2. **休整是否加"回血 vs 强化"二选**：现有 rest 只回血 25%。经典做法给二选，但属新玩法，建议本轮不做。
3. **精英 / BOSS 确认层**：现有 `_show_battle_confirm` 可复用，点节点先看敌人再决定是否进入——建议保留。
4. **旧线性模式去留**：建议保留 `node_mode=false` 的线性模式作为调试 / 回退通道，不删。
