## 1. 逐项核验结果

### 附录 A-1：读取 `growth_loot_offer.gd`，记录品质抽选与候选生成流程

**状态：✅ 已核验**

`GrowthLootOffer` 继承 `LootOffer`，**没有自己的 build 流程**，只覆写 `_rebuild()`：

- 生成链：`reward_system.build_loot_offer(..., growth_only=true)` → `GrowthLootOffer.new()` → `LootOffer.build()`（`:46`）→ `_pool.roll_quality()` 定品质 → `GrowthLootOffer._rebuild()` 取候选。
- `_rebuild()`（`growth_loot_offer.gd:9`）从 `_growth_candidates()` 取候选，按 kind 去重取 3 张，`_fill_conversions()` 补位，`_inject_queued_growth()` 注入队列成长。
- 候选 7 种（`:38-104`）：mastery / symbol / perk / maxhp / shield / heal / queued_growth。

**对 v1.1 的影响**：
- v1.1 §1.1「来源包括武器训练、符号灌注、技艺、待选成长、最大 HP、护盾、回血」**准确**。
- 但 v1.1 §5 想改的"统一候选池"要动的正是 `LootOffer.build()` 的 `roll_quality → tier_items` 两阶段主流程，以及 `growth_loot_offer._rebuild()` 的候选来源——**这是核心改动，不是配置调整**。

### 附录 A-2：读取 `loot_offer.gd`、`reward_system.gd`，核对奖励数据字段与回退行为

**状态：✅ 已核验**

**数据字段**（`scripts/items/reward_data.gd:10-18`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | 效果分发键：heal/maxhp/symbol/shield/power/gold/consumable/weapon/maxhp_heal/elite_* |
| `icon` | String | emoji 占位 |
| `art` | Texture2D | 卡面美术预留位，空则用 icon |
| `label` / `desc` | String | 文案（与数值同文件，防双写漂移） |
| `value` | **int** | 唯一数值字段：heal 为最大 HP 百分比（35=35%），其余为 += 绝对值 |
| `rarity` | String | common / uncommon / rare（三档，**这是房奖励 RewardData 的稀有度，与战利品品质是两套体系**） |

**回退行为**（`loot_offer.gd`）：
- `build()` 失败条件仅两种：`invalid_quality`、`source_not_random:<source>`（`:51-64`），返回 `{ok:false, reason, ...}`。
- 候选不足时 `_fill_conversions()`（`:189`）用同层"金币/伤害"转化卡补齐，不空屏。
- `_rebuild()` 的 avoid 机制：避开上一组路径后不足则补回（`:108-111`），保证同层可用。
- 上层 `room_flow._start_loot_phase()`（`:65-69`）若 `ok=false` → `settle_loot_skip()` → 直接结束战后流程。

**对 v1.1 的影响**：
- 🟡 **品质档数更正（本报告初稿有误）**：项目里有**两套独立的品质/稀有度体系**：
  ① 战利品品质 `LootSourceTable.QUALITIES`（`loot_source_table.gd:16`）= **common/uncommon/rare/epic 四档**，
  用于 `LootOffer` 分层抽取、卡面展示、跳过/转化数值——**v1.1 §8 的四档设计是对的**；
  ② 房奖励稀有度 `RewardData.rarity`（`reward_data.gd:18`）= common/uncommon/rare 三档，
  用于旧 `roll_rewards` 的抽取权重，与战利品品质无关。
  本次重构改的是①，四档成立，§8 无需因档数改写。本报告的"三档"说法仅适用于②。
- ⚠️ `value` 只有一个 int 字段，v1.1 中"双效果卡"（如 SUR-01 回血+护盾、ECO-02 金币+涨价惩罚）**无法用单个 RewardData 表达**，需要新字段或新分发逻辑——这属于 B/C 级改动，不是纯配置。

### 附录 A-7：核对商店购买事件是否能安全提供消费返利

**状态：✅ 已核验**

**对 v1.1 的影响**：

## 2. 核验后对 v1.1 的修订建议（汇总）

### 🔴 必须修订（3 项）

1. ~~品质档数~~ **已更正**：战利品品质确为四档，v1.1 §8 无需改写。真正的双效果字段问题见下条。
2. **双效果卡字段**：SUR-01（回血+护盾）等双效果卡无法用单个 `value:int` 表达，需新增字段或降级为单效果。
3. **§5 统一候选池二选一拍板**：
   - 方案甲（推荐先做）：**兼容模式**——保留 `roll_quality`，仅做有效性过滤 + HP 权重 + 层内多样性，明确记录"类别权重受品质层卡池限制"的技术债。
   - 方案乙：**完整重构**——改 `LootOffer.build()` 主流程，同步改重抽定价/跳过收益/图鉴统计，超出"奖励重构"范围。
   - 当前 9 张 reward 卡池撑不起四类分层采样，强行上方案乙会退化成"每次抽那几张"。

### 🟢 建议调整（2 项）

4. **恢复 CON-03「免费重转」**：`_free_spin()` 现成，且非技艺重复，是操控类奖励的合适载体。
5. **SUR-03 升 A 级**：`run_shield_next` 现成，不必"暂缓"。

### ✅ 确认无误（5 项）

技艺重复判断、BLD-01/02/03 复用策略、POW-03 延期、ECO-03 延期、多敌功能边界。
