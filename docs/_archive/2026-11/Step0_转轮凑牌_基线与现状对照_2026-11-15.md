## 2. 为什么要钉数值，而不是钉「触发了」

方案 Step 1/2 会做两件事：用 `PatternMatcher` 复算 G01–G03、用 S01–S06 替换现有三条永久装备共鸣。

替换期间新旧两套会短暂共存。如果对照只断言「共鸣/三连被触发」，那么**同一次攻击吃掉两份加成也照样能过**。
所以第 60 套的断言全部是**最终伤害数值**或**倍率比值**，删旧效果时才有证据。

## 3. 现状对照的实测结果（这套的价值就在这里）

现有测试（`weapon_archetype_test`）已经钉住了同源三连与元素共鸣，本套补它没覆盖的两块：

### 3.1 同族三连 = 同源三连的 0.75 倍

- 同源（3 格同来源）：用武器专精倍率，本用例 ×2.0 → 108
- 同族（3 格 3 来源）：固定 ×1.5 → 81

`81 / 108 = 0.75` 正好等于 `1.5 / 2.0`。

断言写成**比值**而不是绝对值，因为三个来源的攻击力可能不同，测试不该假装知道绝对值。

### 3.2 三条装备共鸣的真实语义（与方案描述不一致，重要）

| 共鸣 | 资源字段 | 实际效果 | 方案里 S01–S03 的目标 |
|---|---|---|---|
| 烈焰共鸣 | `weight_bonus` = 火斩/燃烧 **+2 权重**<br>`element_boost = ""`（空！） | **只改转轮带权重，完全不加伤害** | 火伤 +25% + 燃烧 +1 层 |
| 冰火二重 | `crit_bonus = 0.5` | 同源三连倍率 2.0 → 2.5（×1.25） | 火冰 20% 转穿透 + 各 +1 层 |
| 黎明圣辉 | `element_boost = "light"`，`element_boost_mult = 1.2` | 光伤害 ×1.2 | 追加一次穿透齐射（50% 攻击和） |

**烈焰共鸣是「更容易摸到」而不是「打得更疼」**：它的 `element_boost_mult = 1.2` 因为绑定的
`element_boost` 是空串而永远不会被 `element_boost()` 取用。

这意味着 Step 2 的 S01 替换是一次**真实的机制变化**（权重 → 伤害），不是「同一效果换个说法」。
这条必须写进对照组，否则将来没人知道为什么手感变了。

## 4. 流程对照锁住了什么

第 61 套钉住三条流程语义：

1. **最后一列停下即结算**：`turn_resolved` 在 `on_spin_pressed()` 返回时已置位
2. **不存在事后换牌状态**：`pending_swap` / `awaiting_swap` / `swap_tokens` / `free_swap_left` /
   `pending_redraw` / `awaiting_redraw` / `swap_window` / `post_settle_pick` 八个字段名逐个检查不存在
3. **结算入口唯一**：`CombatSystem.evaluate`，且 `turn_flow` 持有同一个 `DuelController` 实例

## 5. 过程中踩的坑（都写进测试注释了）

| 坑 | 现象 | 处理 |
|---|---|---|
| `_item_crit_map` 的 key 不是武器路径 | 期望 30、实测 108 | 改用 `ReelSystem.source_key(sym, source)` |
| `SynergySystem._active` 是类型化数组 | `Invalid assignment ... Array` | 改用 `clear()` + `append_array()` |
| 转轮不会自己停 | 流程测试卡在 `await spin_finished` | 用 `stop_next_reel(false)` 模拟三次按停 |
| **运行时错误造成假绿** | 属性名写错（`duel.turn` 应为 `turn_count`），函数中断但仍显示 PASS | 加 `EXPECTED_CHECKS`：检查数少于预期即判失败 |

最后一条最值得记：GDScript 里访问不存在的属性只会打一条 SCRIPT ERROR，然后**中断当前函数**，
但 `fails` 计数不会增加 —— 如果不额外校验检查数，测试会静默通过。
