## 1. 为什么技能术式必须独立成轨

原 24 种方案里的 S05（护盾×2）、S06（增益×2）不可达，根因是 **90 把武器一把都不带 shield/buff 符号** ——
这两类符号只来自技能。

新方案把它改成「技能辅助术式」：**恰好一张技能牌 + 两张武器牌**，用技能牌承担那些
武器永远提供不了的能力（增伤 / 护盾 / 治疗）。这不是放宽条件，而是把「内容该由谁提供」摆正。

## 2. 三条术式

| ID | 名称 | 技能供给 | 组合条件 | 效果 |
|---|---|---|---|---|
| T01 | 增伤术式 | `buff_effect = power / damage_mult`（6 个技能） | 技能增伤牌 + 武器伤害牌 + 任意武器牌 | 本轮**武器**伤害 +15%；技能伤害不计入 |
| T02 | 防御术式 | `kind = shield` / `buff = shield`（8 个） | 技能护盾牌 + 任意两张武器牌 | +8 护盾；敌方为蓄力/重击意图时 +12 |
| T03 | 恢复术式 | `kind = heal` / `buff = regen`（9 个） | 技能治疗牌 + 任意两张武器牌（未满血） | 治疗 +25%；HP≤50% 时标记一次净化 |

## 3. `skill_role`：把三种能力收敛成一个字段

如果直接写 `{"kind": "shield"}`，就会漏掉 `buff_effect = shield` 的那 4 个技能（它们的符号 kind 是 `buff`）；
写两个条件又要 OR，而求解器不支持 OR。

所以在牌面输入里加了一个派生字段：

```text
skill_role = power | shield | heal | ""
    power  ← buff_effect ∈ {power, damage_mult}
    shield ← kind == shield 或 buff_effect == shield
    heal   ← kind == heal 或 buff_effect == regen
```

条件就变成 `{"source_kind": "skill", "skill_role": "shield"}`，一条搞定，且与「一个技能槽」的约束天然一致。

## 4. T01 怎么做到「只强化武器」

`dmg_by_elem` 是混合的，不区分来源类别。所以从 `source_dmg` 里把技能符号造成的伤害筛出来扣掉：

```text
武器伤害 = Σ dmg_by_elem - Σ source_dmg[属于技能符号的 key]
加成 = 武器伤害 × 15%
```

技能符号的 `source_id` 是空串，`source_dmg` 的 key 就落在符号路径上，
正好能用 `_skill_sym_kind` 判归属。

## 5. T03 的满血排除放在选牌阶段

方案要求「满血时 T03 不激活，避免无效候选」。

实现放在 `_apply_patterns()` 的 T 判定之后：

```gdscript
if t_pick != null and t_pick.effect_id == "recovery_support" and player_hp >= player_hp_max:
    t_pick = null
```

放效果里也能做到「不生效」，但那时 `pattern_skill` 已经被写成 T03，
UI 会显示「本回合触发了恢复术式」却什么都没发生 —— 在选牌阶段排除更干净。

## 6. T03 的净化已接通（当日补丁）

原本这一条是空白：`debuff_system` 没有公开的移除接口（只有 `apply` / `has` / `turns_left` / 各种倍数），
净化散在消耗品系统里直接操作 `active`。T03 当时只写了 `acc["recovery_purify"] = true` 的标记。

补丁：把移除逻辑抽成 `debuff_system.purify_one(ctrl) -> String`，优先级固定为

```text
interference（目盲 / 缠绕，直接影响转轮操作） > status（虚弱 / 易伤 / 腐蚀 / 禁疗 / 反噬）
instant 类不是持续减益，不参与
```

返回被移除的 id，没有可净化项返回 `""`。T03 低血线时调用它，把结果写进
`acc["recovery_purify"]` 并在伤害分解里留一行「净化「目盲」」这样的日志。

这条现在是真的生效了，测试也验证了「优先移除干扰类、状态类保留、每次只净化一个」。
