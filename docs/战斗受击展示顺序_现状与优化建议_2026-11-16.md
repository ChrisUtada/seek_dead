# 战斗受击展示顺序：现状梳理与优化建议

> 2026-11-16 13:10。**纯分析，未改代码。**
> 所有「现状」均从代码抽取，附文件与行号。

## 一、现状：一回合内表现调用的真实顺序

入口 `combat_system.evaluate()`（combat_system.gd:180）：

```gdscript
func evaluate() -> void:
    _phase_symbols(acc)            # 不 await
    await _phase_defense(acc)      # 标注 await，但内部无 await
    _phase_counter(counts, acc)    # 不 await
    _apply_patterns(acc)           # 不 await
    await _phase_attack(counts, acc)  # 唯一真正 await 的地方
```

## 二、六个具体问题

### ① 数字与血条都早于动作（最明显）

②③ 先把数值改了，④ 弹飘字，⑤ 才播放挥砍动画。

玩家实际看到的是：**敌人血条先掉 → 数字先跳 → 然后角色才挥刀**。因果倒置。

### ② 同锚点的飘字完全重叠

`popup_pool.popup()`（popup_pool.gd:33）没有堆叠偏移：

```gdscript
lbl.position = Vector2(gp.position.x ..., gp.position.y - pr.position.y + 2)
var tw := create_tween()
tw.tween_property(lbl, "position:y", lbl.position.y - RISE_PX, DURATION)
```

每条飘字都从**同一个起点**上浮。所以：

| 场景 | 重叠的飘字 |
|---|---|
| 金币 + 护盾 + 治疗 | 三条都在玩家锚点，**完全叠死** |
| 主伤害 + 元素爆发 | 两条都在敌人锚点，前后相差不到一帧，**完全叠死** |

### ③ 防御阶段没有任何节奏

`_phase_defense` 虽然被 `await` 调用，但函数体里没有任何 `await`。所以护盾、治疗、溢出转盾在同一帧内全部执行完，三条飘字同时出生。

### ④ 破甲归零没有专门表现

`apply_enemy_damage(normal, false)` 和 `(pierce, true)` 是两次调用，但只弹**一个总伤害**数字。护甲被打空这个关键节点，玩家只能靠自己读角落里的护甲数字发现。

### ⑤ 没有命中定格（hit stop）

唯一的时间控制是结尾 `await 0.35s`。没有「命中瞬间短暂定格 → 数字弹出 → 继续」的节奏，打击感偏软。

### ⑥ 底部反馈与飘字同时出现

`_show_turn_feedback` 在 ⑧ 立刻执行，与 ④ 的伤害飘字同一帧。底部文字和场上飘字会互相抢注意力。

## 三、建议的目标时序

### A. 玩家攻击段（核心，优先级最高）

```
1. 挥砍起手           0.12s 前摇
2. 命中帧             弧光/爆点峰值
3. 命中定格           0.05~0.08s（hit stop，时间缩放或直接停帧）
4. 伤害数字           从敌人身上弹出，带冲击缩放
5. 血条/护甲条扣减     数字之后 0.04s（让数字先出、血条跟随）
6. 破甲提示           若护甲归零 → 单独一行「护甲破裂」+ 颜色
7. 元素爆发（若有）     单独第二段，与 4 错开 ≥0.2s
8. 底部反馈           主伤害飘字淡出后再出
```

### B. 玩家增益段（金币 / 护盾 / 治疗）

```
1. 护盾     🛡+N
2. 治疗     ❤+N      间隔 0.12s
3. 金币     💰+N      间隔 0.12s
```
顺序改为「防御 → 资源」，且每条之间留间隔，不要同帧。

### C. 敌方攻击段

同样问题：`enemy_system.gd:59` 先弹飘字再 `enemy_deal_damage`。应改为「抬手 → 命中 → 定格 → 数字 → 血条」。

## 四、改动建议（按性价比排序）

### 第一优先 · 飘字堆叠偏移（改动最小、收益最大）

`popup_pool.popup()` 增加「同锚点活跃飘字计数」，每条额外上移固定像素：

```gdscript
# 概念示意
var offset := _active_at(anchor) * 12.0
lbl.position.y -= offset
```

这一条能让现有的所有重叠立刻消失，**不需要动任何结算代码**。

### 第二优先 · 调整顺序（低风险）

在 `_phase_attack` 内把三件事重排：

| 现在 | 改为 |
|---|---|
| 扣血 → 飘字 → 动画 | 动画起手 → 扣血 → 飘字 → 刷新血条 |

具体做法：`play_attack` 改为返回 `Signal` 或加 `await`，让数值改动落在动画的命中帧之后。

代价：`play_attack` 是 void，改成 awaitable 会牵动所有调用点（敌方攻击也用）。**建议只加一个可选的 `hold_until_impact` 参数**，不改默认行为。

### 第三优先 · 防御阶段加间隔

在 `_phase_defense` 的 shield / heal / gold 三处之间插入 `await create_timer(0.12).timeout`。

注意：`_phase_defense` 已被 `await` 调用，所以直接加 `await` 即可生效，不用改调用方。

### 第四优先 · 命中定格

在命中帧做 `Engine.time_scale = 0.15` 持续 2~3 帧再恢复，或直接 `await create_timer(0.06)`。

风险：时间缩放会影响飘字 tween。建议用**纯等待**而不是 time_scale，简单且无副作用。

### 第五优先 · 破甲独立反馈

`apply_enemy_damage` 里检测「本次调用把 armor 从 >0 打到 0」，返回一个标记，由 `_phase_attack` 决定是否额外弹一条「⚔ 护甲破裂」。

## 五、需要注意的约束

| 约束 | 说明 |
|---|---|
| **RNG 不可污染** | 任何新增的随机（如飘字横向抖动）必须用 `RandomNumberGenerator` 实例，不能用全局 `randf_range`，否则同种子不同结局 |
| **演示时序不得改变结算** | 所有停机/等待只能在表现层，不能插到 `apply_enemy_damage` 之前影响数值 |
| **敌方回合共用同一套动画** | `play_attack` 被双方调用，改签名要同时验证两条路径 |
| **等待总时长要控制** | 现在一回合固定 0.35s。加 3 处 0.12s 间隔后约 0.7s，需实测是否拖沓；建议把总时长压回 0.5s 内 |

## 六、建议的落地顺序

1. **先做飘字堆叠偏移**（独立、无风险、立竿见影）
2. **再做防御阶段间隔**（3 行代码）
3. **然后做攻击段顺序调整**（需要改 `play_attack`，影响面最大，单独验证）
4. 命中定格与破甲反馈作为打磨项，最后做

前两步加起来改动很小，就能解决「数字糊成一团」和「看不到自己加了什么」两个最直接的体感问题。

## 七、可以顺手确认的两件事

1. **底部反馈条与飘字的视觉冲突**：现在两者同帧出现，建议错开。你实际玩的时候有没有觉得底部那行字来得太快、来不及读？
2. **0.35s 够不够**：如果你觉得整体节奏偏快或偏慢，这个值是最直接的调节旋钮，可以先单独调它再决定要不要加分段。

## 八、第一 / 第二步 已实施（2026-11-16 13:20）

按「先做前两步」的要求，只动了飘字层与收益飘字节奏，**没有碰攻击段顺序、没有改 `play_attack`**。

### 步骤一 · 飘字堆叠偏移

`scripts/ui/popup_pool.gd`

```gdscript
const STACK_STEP := 13.0
const STACK_MAX := 4
var _stack_depth: Dictionary = {}   # anchor instance_id -> 当前活跃飘字条数
```

- `popup()` 记录该锚点当前活跃条数，第 N 条起始 y 上移 `N × 13px`
- 归还时（`_return_popup` 增加 `key` 参数）递减并清理空键
- 上限 4 层，避免堆太高被推出屏幕

**这一条同时解决了「主伤害 + 元素爆发叠死」** —— 两者都在敌人锚点，现在会自动错开。

### 步骤二 · 收益飘字节奏

`scripts/battle/combat_system.gd`

```gdscript
const POPUP_BEAT := 0.12
var _popup_fired_this_turn: bool = false

func _popup_gain(text, color, anchor) -> void:
    if _popup_fired_this_turn:
        await _ctrl.get_tree().create_timer(POPUP_BEAT).timeout
    _popup_fired_this_turn = true
    _ctrl.hud._popup(text, color, anchor)
```

| 飘字 | 是否走节奏 | 说明 |
|---|---|---|
| 金币 | ❌ 只打标记 | 它在 `_phase_symbols` 里，**该函数是同步调用**，引入 await 会把符号结算中途挂起、打乱后续贡献顺序 |
| 护盾 / 治疗 / 状态 | ✅ | 第一条立即弹，之后每条前插 0.12s |
| 伤害 | ❌ 不参与 | 必须紧跟扣血；延迟会加剧「血条先变、数字后到」 |

`_popup_fired_this_turn` 在 `_reset_turn_state()` 里清零，所以每个回合第一条收益飘字永远是零延迟。

### 实际效果（金币 + 护盾 + 治疗 的回合）

```
t=0.00s  💰+2
t=0.12s  🛡+8   （比第一条高 13px）
t=0.24s  ❤+5   （比第一条高 26px）
```

时间与空间双重错开，不再是一帧刷出三条。

### 验证

- `--headless` 加载无报错、无协程相关警告
- 全库确认 `_return_popup` 无旧签名残留调用

### 未做（需你确认后再动）

- 攻击段顺序重排（`play_attack` 要改成可 await，敌我共用）
- 命中定格、破甲独立反馈

### 一个需要你实测的数值

`POPUP_BEAT = 0.12` 是单处间隔。极端回合（金币 + 护盾 + 治疗 + 状态四条）会额外增加 0.36s 展示时间。如果觉得偏慢，这个常量是唯一旋钮，调到 0.08 即可。

## 九、连线方案被否决 → 改为逐格扫描（2026-11-16 13:40）

先按方案 B 实现了「格间空隙画金色连接条」，实测**视觉上很丑**，被否决。原因复盘：

- 连接条只能画在 10px 的格间空隙里，成品是两小段 14×5px 的色块
- 它既不像线（太短），也不像框（不包围），读起来像「格子上粘了两块补丁」

**改为逐格扫描（方案 A 的纯视觉版）**：三格边框按 左→中→右 依次亮起并淡出。

### 实现（battle_hud.gd）

| 项 | 值 |
|---|---|
| 每格亮起 | 边框瞬间不透明 + 弹缩一次（复用 `_set_cell_pop`，与停轮闪光同曲线） |
| 格间间隔 | `CELL_SWEEP_STEP = 0.07s` |
| 单格衰减 | `CELL_SWEEP_DECAY = 0.18s`（下一格亮起时上一格仍在淡出 → 扫过感） |
| 三连收尾 | `settle_cell_sweep()` 三格一起再亮一次，衰减 0.22s |

样式沿用停轮闪光的「全透明底 + 2px 金边」，但用**独立 Panel 与独立 Tween**，避免和 `cell_stop_tweens` 争用。

### 节奏

| 项 | 变化 |
|---|---|
| 逐格扫描 | +0.21s（3 × 0.07） |
| 防御阶段尾部等待 | 0.25s → 0.10s |
| **净增** | **约 0.06s** |

### 为什么还是只做视觉、不做逐格结算

见第八节：结算按「符号 + 元素」聚合、三连判定依赖完整行统计，
逐格结算会形成循环依赖。扫描只负责让玩家看清「这一行是哪三格」。
