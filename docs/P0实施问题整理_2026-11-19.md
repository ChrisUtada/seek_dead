## 2. 详细问题与解决

### 问题 1：技艺卡"始终构造"与 8% 类别权重的语义冲突

**现象**：V1.1 §21 要求"取消 15% 独立注入，由 skill 类别 8% 权重控制"，但当前技艺卡只在
`growth.should_offer_perk()`（15% 概率）为真时才构造进 extra——若直接删掉 15%，skill 类别
将永远没有候选，8% 权重形同虚设，技艺只在保底时出现一次。

**解决**：技艺卡**始终构造进 extra**（`_draft_extra()` 里遍历 `growth.roll_choices()`），
作为 skill 类别候选参与 8% 权重抽取；保底时由 `force_skill` 绕过权重强制注入。
这样既取消了 15% 独立机制，又让 8% 权重真正生效，符合"单一权重体系"。

### 问题 2：保底重抽会因过早 mark 而丢失强制技艺

**现象**：最初实现在 `compose()` 后立即 `mark_skill_offer_satisfied()`——但若玩家重抽，
`should_force_skill()` 已变 false，重抽后的 Draft 不再强制含技艺，违反 V1.1 §21
"保底 Draft 重抽后仍须包含技艺"。

**解决**：把保底标记改为**房间级**（`_force_skill_this_room`），在玩家**结算或跳过**时才 mark：
- 保底房：`should_force_skill()` 在整个房间期间保持 true，每次 compose（含重抽）都强制注入；
- 非保底房：自然出现技艺时立即 mark（完成保底）；
- 结算/跳过时：展示过即完成，不强求选择（符合 §21"保底只保证候选出现"）。

### 问题 3：符号灌注 +1 权重不产生格数变化

**现象**：首版符号权重奖励用 `weight=1`，Resolver 返回 `no_cell_change` 失败。
根因：`ReelSystem.cells_for()` 阈值是 w<2→2格、2≤w<4→3格、w≥4→4格，+1 不跨阈值。

**解决**：权重步长改为 **+3**（与现有"符号灌注"奖励一致，+3 必跨一格可见）。
同时发现部分符号（如 burn）基础权重已满 4 格，再加也不会变——
`_make_symbol_weight_defs()` 增加 `_symbol_cells(sym,0) >= 4` 过滤，跳过满格符号。

### 问题 4：pool_items 结构误判

**现象**：`_make_symbol_weight_defs()` 首版把 `pool_items` 当成二维数组
（`for it in pool: var sym = it[0]`），生成 0 张卡。
根因：`pool_items` 每项实为 Dictionary `{"name","hit","syms":[[SymbolData,weight,elem,wid,power],...]}`。

**解决**：改为按 `it.get("syms", [])` 遍历二维数组，符号在 `entry[0]`。

### 问题 5：Resolver 实际只支持 6 个 effect_id（部分解决）

**现象**：规格 §10.2 列出 `run_symbol_bonus`/`pattern_bonus`/`reel_control`/`consumable_add` 等接口，
但核查 `reward_resolver.gd` 发现实际只支持 6 个：`heal`/`shield_next_battle`/`run_power_bonus`/
`flame_affinity`/`pick_perk`/`learn_signature`。

**解决**：
- `run_symbol_bonus`：新增 Adapter 复用 `_apply_loot_option({kind:"symbol"...})` ✅
- `gold_add`：新增 Adapter 复用 `{kind:"item",grant:"gold"}` ✅
- **`pattern_bonus` / `reel_control` / `consumable_add`：未实现**——
  `pattern_effects` 静态读 `.tres` 参数，无运行时通用强化通道；操控无独立接口；
  消耗品补充的 `item` 分支需要 offer 上下文。按规格"禁止臆造接口"暂缓到 P1+。
  这也意味着 P0 的 `rule_mod`/`reel_control` 类别暂时只有极少数/无候选。

### 问题 6：三选一数量硬断言

**现象**：新增 `seed_gold_cache.tres` 后，`reward_p2_test` 的"19 seed defs loaded"断言失败（实为 20）。
**解决**：测试断言同步改为 20。这暴露了测试对内容数量的硬编码脆弱性——
未来加卡需同步改断言，建议后续改为"≥N"的弹性断言（本次未改，保持最小改动）。

### 问题 7：check-only 模式报 SaveSystem 未声明

**现象**：用 `--check-only --script` 检查测试脚本时报
`Compile Error: Identifier not found: SaveSystem`，但场景正常运行无此错误。
**诊断**：`SaveSystem` 是 autoload 单例，`--check-only` 模式不加载 autoload，
所以静态检查会误报。正常运行（`.tscn` 场景）没问题。
**结论**：工具误报，非代码缺陷。检查脚本语法用 editor 模式或场景运行，不要用 check-only 判断运行时可用性。

### 问题 8：GDScript 类型推断错误

**现象**：多处 `var cat := d.effective_category()` 报
`Cannot infer the type of "cat" variable because the value doesn't have a set type`。
根因：`d` 来自未类型化 `Array`（Variant），其方法返回值无法推断。
**解决**：改为显式类型声明 `var cat: String = d.effective_category()`。
此问题在 `draft_composer.gd`、`p02`、`p04` 均出现过，是本项目 GDScript 的高频坑。

### 问题 9：Draft 存档恢复无 Run 存档系统可扩展（留空）

**现象**：规格 §11 要求当前 Draft/重抽状态存档、中断恢复不重抽。
核查发现项目**只有 meta 跨局存档（meta_store.gd），没有 Run 存档系统**；`battle_state.gd` 是只读快照不持久化。

**决策**：按 V1.1 §11.2 前提"若当前项目已有 Run 存档结构，应在既有结构扩展，
不建立第二套 Run Save 系统"——前提不成立，故**不新建第二套 Run 存档**，本项留空。
这是规格在当前工程的适用性限制，不是遗漏。若未来引入 Run 存档，需补此块。

## 5. 经验教训（供后续参考）

1. **先核查真实接口再写代码**：规格文档列的接口名与实际代码可能不符（问题 5），
   动手前必须读 `reward_resolver.gd` 等真实实现。
2. **数值奖励要验证"可见变化"**：格数阈值类机制，+1 可能无效（问题 3）。
3. **保底/一次性状态的 mark 时机很关键**：过早 mark 会让重抽丢失约束（问题 2）。
4. **GDScript 显式类型**：从 Array 元素取方法返回值时，一律显式标注类型（问题 8）。
5. **check-only 不载 autoload**：不要用 `--check-only` 判断含 autoload 依赖的脚本可用性（问题 7）。
6. **测试数量断言用弹性写法**：硬编码"19 张卡"会在加内容时误报（问题 6）。
