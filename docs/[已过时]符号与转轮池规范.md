## 0. 为什么需要这份规范

当前转轮池的"稀有度"是**隐式涌现**的：每把武器手写 reel 权重 → 合并后整数铺格 → 频率随武器数膨胀而负向缩放（武器越多，special/状态等关键符号越被埋）。这会导致：

- 后期某些符号整房不出现（已实测体感）；
- "爽点符号"（连锁 special / 破甲 pierce / 克制核爆）恰恰被埋得最深，与"后期不够爽"自我闭环；
- 未来每加一个符号都靠手感调权重，无统一标尺，雪球越滚越乱。

本规范把"经典老虎机稀有度分层"沉淀为**数据契约 + 治理规则**，让加符号变成填空，而非重新调参。

---

## 1. 不变前提（设计哲学）

1. **老虎机家族 → 非均匀 + 显式稀有度**（不是三消家族的均匀随机）。符号稀有度是设计出来的稳定属性，稀有 = 兴奋 = 高赔信号。
2. **策略在 build 层，战斗内不黑箱**：轮面可见、频率透明，不像隐藏乘数。
3. **稀有度全程稳定，不随武器/技能数量负向缩放**。经典里"7"永远占实体轮固定格数，不会因你是老玩家变 1/200。
4. **武器/技能只增"种类广度"，不稀释已有符号的频率档**。
5. **稀有度是奖励信号，不是惩罚性"永不出现"**——RARE 档必须有硬保底。

---

## 2. 稀有度分层契约（核心）

每个符号必须归入且仅归入一个档。档位决定**目标频率区间**与**保底**，治理层（`_build_strips`）据此强制，无需手工精调权重。

| 档 Tier | 目标频率/列 | 保底（单列） | 角色 | 典型 `kind` |
|---|---|---|---|---|
| **COMMON** | 合计 25–35% | 无（自然高） | 基础输出 / 元素主伤害 | `damage`、`status`（作为主伤害者） |
| **UNCOMMON** | 合计 8–12% | ≥1 格 | 防御 / 铺垫条件（护盾、治疗、次要状态） | `shield`、`heal`、非主伤 `status` |
| **RARE** | 3–6% | **硬保底 ≥2.5%（或 ≥2 格）** | spike / 核爆触发（连锁、克制元素三连） | `special`、未来克制核爆符号 |
| **UTIL** | 固定 5–8% | 固定 | 经济 | `gold` |
| *FILLER* | 受控 | — | 稀释刹车（见 §4 G5），**不计入上四档的奖励稀有度** | `trash` |

**新符号定档决策规则**（一句话）：
> 这个符号命中后是 **baseline 输出**（COMMON）、**铺垫/防御条件**（UNCOMMON）、还是 **spike/核爆触发**（RARE）？经济辅助 = UTIL。

### 2.1 推荐落地：给 `SymbolData` 增加 `rarity_tier` 字段

`scripts/battle/symbol_data.gd` 现有 `kind` 字段同时承担"结算行为"与（隐式）"稀有度"。建议**新增独立字段**：

```gdscript
@export var rarity_tier: String = "common"   # common | uncommon | rare | util | filler
```

- 数据即契约：每个 `.tres` 显式声明档位，治理层直接读，不靠记忆或 `kind` 推导。
- `kind` 继续管结算行为；`rarity_tier` 管频率治理。两者解耦。
- 这是"统一规范处理方式"最干净的实现锚点。

## 3. 转轮池构建管线（现状，待治理）

- **`_build_pool`**：合并所有已装备武器 + 技能的符号为加权池；**共享符号权重累加**（`merged[mkey][1] += weight`）；金币常驻 `GOLD_POOL_WEIGHT = 3`。
- **`_build_strips`**：每个符号按 `round(weight)`（**下限 1 格**）复制成整数格铺进 `base`；每列 = 同一 `base` 的洗牌副本。概率 = 该符号格数 / 总格数。**`trash` 不再来自武器手写权重**（S5 已移除），改为池级按 `act` 注入的稀释预算（见下）。
- **治理落地状态**（S1–S8 全部落地，替代原"待优化缺口"）：
  - 稀有度字段（`rarity_tier`，S1）→ 数据即契约，治理层直接读，与 `kind` 解耦；
  - RARE 档硬保底（`_enforce_tier_floor_for("rare",...)`，S2 G2）→ 已解决"RARE 滑到 1/N"；
  - UNCOMMON 档保底（`_enforce_tier_floor_for("uncommon",...)`，S3 G1）→ 防防御/治疗符号被埋；
  - 保底按分数随带长缩放 → 吸收"武器数膨胀稀释"（G3）；
  - `trash` 池级受控注入（`TRASH_BASE_FRAC`+`TRASH_ACT_STEP`，S5 G5）→ 替代原各武器手写、成为可调稀释旋钮；
  - 单符号占比上限（`_enforce_symbol_cap`，S4）→ 已解决"`burn` 式垄断"；
  - special 多源 + RARE 上限（`special.tres` 接入 7 武器，S6）→ RARE 不再绑定单一武器；
  - WILD 百搭注入（`WILD_FRAC`，S8）→ 受控帮补 special 连线，提高爽点命中。

## 4. 治理规则（待实现，优化时落地）

- **G1 稳定档频率**：池超阈值时 renormalize，把每档锁回 §2 目标带（少 pad COMMON、保 RARE 下限）。
- **G2 RARE 硬保底**：保证"整房不出现"不可能发生——这是修复"后期不够爽"的关键。
- **G3 不随武器数缩放**：武器只加种类广度，不稀释已有档频率。
- **G4 可见轮面**：玩家能看到轮上有什么、大概多频繁（透明哲学）。
- **G5 受控 trash（受控稀释）**：把"各武器手写 trash 权重"改为 **pool 级按 ante/房间注入的稀释预算**，让稀释变成可调旋钮，替代"挤掉符号"成为难度刹车；与 ante 曲线 / 速度协同。
- **（可选）WILD / 对齐符号**：经典老虎机用 wild 提高稀有组合命中率却不让稀有符号变多；可借一个"对齐"符号帮补 special 连线。
- **（可选）RTP 式 KPI**：定义"爆炸命中频率"目标（如 special 三连期望每房 ≥1 次），反推 RARE 档下限，把"爽点频率"变成可调旋钮。

## 6. 新增符号标准流程（SOP）

未来任何"加符号"都走这套，不另起炉灶：

1. 在 `resources/symbols/` 新建 `<id>.tres`，填 `SymbolData` 全部字段（见 §7 字段表）。
2. **必填 `kind`**（决定结算行为）；**建议填 `rarity_tier`**（§2.1，未落地前先按 §2 决策规则手记档位）。
3. 依 §2 决策规则定档：baseline→COMMON / 铺垫防御→UNCOMMON / spike核爆→RARE / 经济→UTIL。
4. 把符号加入目标武器/技能的 `reel`（`SymbolWeight{symbol, weight}`），`weight` 初值参照该档目标频率相对同武器其它符号的比例。
5. 治理层（`_build_strips`）保证档位频率/保底，无需手工精调。
6. 检查：是否需在 `_evaluate` / `_on_counter` 增加结算分支（如新 `kind`）。

## 7. `SymbolData` 字段表（元数据契约）

`scripts/battle/symbol_data.gd` 当前字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `label` | String | 图标（emoji） |
| `name` | String | 显示名 |
| `kind` | String | **`damage`\|`shield`\|`heal`\|`status`\|`special`\|`buff`\|`trash`\|`gold`**（结算行为分支依据） |
| `rarity_tier` | String | **`common`\|`uncommon`\|`rare`\|`util`\|`filler`**（频率治理契约；S1 已落地）。`kind` 管结算、`rarity_tier` 管频率，二者解耦。 |
| `base` | float | 伤害/数值基准 |
| `element` | String | `fire`\|`ice`\|`poison`\|`light`\|`dark`\|`none`（单向克制） |
| `status_type` | String | 仅 `kind=="status"`：`burn`\|`frost`\|`poison` |
| `color` | Color | 显示色 |
| `pierce_armor` | bool | 直接扣 HP、不先扣护甲（破甲） |
| `buff_effect` / `buff_value` / `buff_turns` | — | 仅 `kind=="buff"` 自描述效果 |

> 新增符号时**必须**同步确认：是否需要新 `kind` 分支、`element` 克制关系、`pierce_armor` 是否破甲。
