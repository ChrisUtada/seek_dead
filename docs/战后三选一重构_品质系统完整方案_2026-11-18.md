# 战后三选一重构｜品质系统完整重构方案（最佳方案）

> 日期：2026-11-18
> 定位：一次性做对的**完整重构**方案，非兼容模式。
> 适用：普通/精英房 `GrowthLootOffer`（本次目标）；BOSS 奖励流程保持隔离、不动。
> 依据：源码核验（见 `docs/战后三选一重构_附录A核验报告_2026-11-18.md`）。
> 本文是设计方案，**未修改任何游戏代码**。

---

## 0. 为什么完整重构是可行的（先给信心）

完整重构的最大顾虑是"品质被很多地方依赖，动它会连锁爆炸"。核验后的事实是：

- **结算完全不读品质**：`settle_loot_offer()` 里没有任何 quality 引用。品质只影响「生成选层 / 卡面展示 / 跳过与转化数值查表」三处。
- **品质决策点只有一个**：`LootOffer.build()` 调一次 `roll_quality()`，再用 `tier_items(source, act, quality)` 选层。
- **下游依赖面很小**：全项目 quality 相关引用约 21 处，集中在 `loot_offer.gd` / `loot_pool.gd` / `loot_source_table.gd` / UI 两个文件。

所以完整重构的爆炸半径可控，不需要重写结算、存档、战斗。

---

## 1. 核心设计：品质从「前置闸门」改为「卡的固有属性」

### 1.1 现在的模型（问题所在）

```
roll_quality(source) → 得到一个品质层
        ↓
tier_items(source, act, quality) → 只从这一层取 3 张
        ↓
卡面显示品质
```

问题：**品质先定，决定了候选只能在同层里挑**。如果某层没有某类别的卡，类别保障就落空；为了凑类别只能反复重抽或塞转化卡。

### 1.2 重构后的模型（最佳方案）

```
统一有效候选池（全品质、全类别的卡）
        ↓
每张卡自带 quality 属性（固有）
        ↓
按「类别权重 × 卡权重 × 品质权重 × 上下文权重」逐张抽 3 张
        ↓
每张卡展示自己的品质（可能三张品质不同）
        ↓
重抽 / 跳过 / 转化数值全部从「每张卡自己的 quality」读
```

关键改变：**quality 从"一次抽、全局共享"变成"每张卡自带"**。这一步同时解决了三件事：
- 类别保障不再受品质层卡池限制（全品质池里选）；
- 品质仍有意义（影响卡的数值、卡面颜色、跳过收益），但不阻断类别；
- 重抽逻辑天然一致（重抽就是重抽 3 张带各自品质的卡）。

## 2. 目标架构（分层职责）

```
┌─────────────────────────────────────────────┐
│ RewardDraft（新）                             │
│ 统一候选生成 + 分层抽选 + 多样性约束           │
│ 输入：上下文(context)                         │
│ 输出：3 张卡（每张自带 quality/category/tags） │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│ RewardCandidate（新，Resource 或轻量 Dictionary）│
│ 统一卡片描述：id / category / tags / quality /  │
│ value / effect_id / validity_check / 文案       │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│ LootOffer / GrowthLootOffer（改造）           │
│ 只负责：冻结 payload、重抽、跳过、结算桥接      │
│ 不再负责 roll_quality / tier_items 选层        │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│ UI（card_factory / reward_screen）            │
│ 从每张卡读自己的 quality 显示颜色/名称         │
│ 「三项同层」文案改为「品质各异」文案            │
└─────────────────────────────────────────────┘
```

## 3. 数据结构：统一候选卡

新增一个统一的候选描述（`RewardCandidate`），把目前散落在三处的卡信息收口：

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `id` | String | 现有 | 效果分发键，复用现有 apply_reward 分支 |
| `category` | enum | 新增 | Survival/Power/Build/Economy（v1.1 §4 四类） |
| `tags` | Array[String] | 新增 | fire/gold/scrap/aim/armor/triple 等（v1.1 §7） |
| `quality` | String | 新增（卡自带） | common/uncommon/rare/epic |
| `value` | int/float | 现有 | 效果数值 |
| `effect_id` | String | 新增 | 指向结算逻辑（复用 apply_reward 的 id 即可） |
| `validity` | Callable/Dict | 新增 | 有效性判定（满级/无目标/已拥有等） |
| `base_weight` | float | 新增 | 卡基础权重，默认 1.0 |
| `title/desc/tooltip` | String | 现有 | 文案 |

> 注意：现有 `RewardData` 只有 `value:int` 一个数值字段，双效果卡（回血+护盾）表达不了。
> 统一候选卡应支持 `effects:Array[{id, value}]`，一次抽卡可携带多个效果——这是完整重构顺带解决的一个 v1.1 硬伤。

## 4. 抽选算法（一次做对的核心）

### 4.1 分层采样（避免类别比例被卡数量放大）

```
1) 过滤：全候选中取 valid（未满级/有目标/未重复/条件成立）
2) 类别权重：BASE_WEIGHTS 经 HP/Build/经济/重复疲劳修正 → 只对"有有效卡的类别"归一化
3) 抽类别：按 category_weight 抽一个类别
4) 抽卡：在该类别有效卡中，按 base_weight × quality_weight × context_weight 抽一张
5) 软惩罚：降低已选卡的类别/标签权重（diversity_factor 0.65–1.0，不绝对禁用）
6) 重复 3)4)5) 直到 3 张
7) 多样性校验：≥2 类别、最多 2 同类、同功能最多 1 张；不满足则逐级放宽
8) 兜底：仍不足则放宽标签/类别限制 → 回到现有有效奖励 → 允许少于 3 张或跳过，绝不塞假卡
```

### 4.2 品质权重（这是与兼容模式最大的不同）

- 品质不再是"先抽一次决定全组"，而是**每张卡按 `quality_weight` 参与抽取**。
- `quality_weight` 由来源表决定（normal 70/25/5/0、elite 20/50/27/3、boss 0/10/60/30、chest 35/40/22/3），
  但对每个类别分别归一化——保证"稀有卡更容易出现在 Build 类"这类设计意图可实现，同时不会阻断其他类别。
- 卡面展示三张卡**各自的品质**（颜色/名称），UI 文案从"三项同层"改为"品质各异，按用途与构筑选择"。

### 4.3 重抽与跳过（一致性改造）

- 重抽：重新执行一次 4.1 全流程，3 张卡各自的新品质；费用规则（5 + 5×次数）不变。
- 跳过收益：从"按全组品质"改为"按 3 张卡里最高品质"查 `loot_skip_gold` 表（或取平均，需拍板一个）。
- 转化/熟练数值：从"按全组品质"改为"按该卡自己的 quality"查表——这个改动让数值更精确。

## 5. 分阶段落地（一次性做完，但分步提交）

> 目标是一次性做到位，但用分步提交控制风险。每步都可独立运行、回归。

| 步骤 | 内容 | 涉及文件 | 风险 |
|---|---|---|---|
| S1 | 建立 `RewardCandidate` 统一卡结构；把现有 7 种成长候选 + 9 张 RewardData 映射进来 | 新增 `reward_candidate.gd`，改 `growth_loot_offer.gd` | 中 |
| S2 | 实现 `RewardDraft` 分层抽选算法（过滤/权重/多样性/兜底） | 新增 `reward_draft.gd` | 中高（算法核心） |
| S3 | 品质改为卡自带；改卡面展示、跳过收益、转化数值的读取源 | `loot_offer.gd`、`card_factory.gd`、`reward_screen.gd` | 中 |
| S4 | 重抽/跳过/冻结 payload 桥接到新结构；保持结算接口不变 | `reward_system.gd`、`loot_offer.gd` | 中 |
| S5 | 状态权重接入（HP/Build/经济/重复疲劳）；v1.1 的 12 张卡数据分批加入 | `reward_draft.gd`、`resources/rewards/` | 低 |
| S6 | 完整回归：普通/精英全 HP 段、重抽、跳过、空池兜底、RNG 可复现 | 测试 + F6 真机 | — |

**不动的部分**：`settle_loot_offer` 结算逻辑、BOSS 奖励、存档、战斗系统、商店/铁砧经济。

## 6. 与 v1.1 其他章节的对接

- §4 四类权重：直接采用，作为 `RewardDraft` 的 `BASE_WEIGHTS`。
- §5.3.1 分层抽选：本方案 4.1 就是它的完整实现（不再有"兼容模式"的妥协）。
- §7 Build 标签：作为 `RewardCandidate.tags`，用于 context_weight 和多样性软惩罚。
- §6/8–11 的 12 张卡：在 S5 分批加入；其中 SUR-03/CON-03 用现成接口（`run_shield_next` / `_free_spin`），
  POW-03/ECO-03 仍按 C 级延期（本重构不解决它们的钩子问题）。
- §13 重抽/跳过：费用不变，收益读取源改为卡自带品质（见 4.3）。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 分层采样算法出现类别比例失真 | S2 单独写单测：给固定候选池，验证类别分布符合 BASE_WEIGHTS |
| UI 仍按"同层三选一"写死文案 | S3 显式改 `reward_screen.gd:136-139` 的标题/tooltip，并加"品质各异"用例 |
| 结算桥接回归（冻结 payload 下标错位） | S4 保持 `payload_at(index)` 接口签名不变，内部映射到新结构 |
| 卡池不足导致兜底退化 | 4.1 第 8 步逐级放宽 + 现有有效奖励兜底，禁止假卡 |
| RNG 污染战斗 | 全程用 `LootPool._rng`（有 seed），不碰 `randf()` |

---

## 8. 结论

一次性做对的完整重构，**核心只有一句话**：把品质从"抽卡前置闸门"改成"每张卡自带的属性"。
这一步做完，v1.1 想要的类别保障、状态权重、构筑协同、12 张机制卡才有稳定的承载基础，
且不必先做兼容模式再返工。爆炸半径经核验可控（结算不读品质、依赖面约 21 处），
建议按 S1–S6 分步提交，每步回归。
