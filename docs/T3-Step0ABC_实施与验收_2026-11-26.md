## 2. 0A · 来源判定（Q5）

### 2.1 代码

`scripts/battle/pattern_matcher.gd` `card_meta()`：技能分支原先**先于**武器分支判定，
共享符号（同一符号既属于已装备技能、又由武器产出）会被误判为 `skill`。改为：

```gdscript
if String(entry["source"]) == "" and ctrl != null and ctrl._skill_sym_kind != null \
        and ctrl._skill_sym_kind.has(sp):
    ...
elif String(entry["source"]) != "" and ctrl != null and ctrl._source_element_map != null \
        and ctrl._source_element_map.has(String(entry["source"])):
    entry["source_kind"] = "weapon"
```

武器分支与 `source_element` 赋值未动。实盘 `cards_from_grid()` 与预览
`_preview_candidate_cards()` 都调用 `card_meta()`，因此两条路径同时修正，没有第二套判定。

## 3. 0B · `source_path`（Q1）

### 3.1 代码

`card_meta()` 初始化 `"source_path": ""`；武器分支命中时追加：

```gdscript
if ctrl._weapon_data_by_id != null and ctrl._weapon_data_by_id.has(String(entry["source"])):
    entry["source_path"] = String(ctrl._weapon_data_by_id[String(entry["source"])].resource_path)
```

技能 / 金币 / MISS / 废铁 / 精华的 `source` 为空，`source_path` 保持空串。

### 3.4 ComboCatalog 复核

- `ComboCatalog.preview_third_slot()`：候选由调用方（`DuelController._preview_candidate_cards()`）
  用 `PatternMatcher.card_meta()` 构造，catalog 只做 `solve_rule`，不自行判来源。
- `ComboCatalog.build_rows()`：只读 `last_acc` 的命中 / 牌谱行，不读取牌卡来源。
- 结论：预览与实盘同源，无需新增第二套判定。

## 4. 0C · 基础攻击契约（Q2）

### 4.1 代码核查

`DuelController.weapon_power_in_slot()` 的实现就是
`int(res.base_power) + weapon_slots.forge_bonus(slot) + _forge_styles.power_bonus(path)`：

- 不读 `mastery`（武器熟练只影响带子 / 调律，见 `WeaponMastery`）；
- 不读遗留字段 `WeaponData.damage`；
- 本轮未修改该函数（仅用契约测试锁住行为）。

### 4.3 文案核查

在 `scripts/ui`、`scripts/items`、`scripts/systems`、`scripts/battle` 全量搜索「基础攻击」，
未发现任何「基础攻击含熟练」口径的文案：

- `card_factory.gd:85` 注释为「锋铸后的真实基础攻击」；
- `weapon_mastery.gd` 的「基础攻击」只出现在锋铸说明与候选描述（锋铸属于槽位锻造）；
- 项目内没有 `item_tooltip.gd`，武器 tooltip 逻辑在 `item_card.gd` / `player_panel_view.gd` /
  `symbol_tooltip.gd`，其中未把熟练计入基础攻击。

结论：无需改文案；未做无依据的文案改动。
