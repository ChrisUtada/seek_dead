# G5 自动记录（替代手填记录表）

> 日期：2026-11-08
> 对应：`docs/统一制作执行计划_2026-11-06.md` §9 / §14 G5
> 目的：边玩边记客观数据，局末自动生成预填记录表；主观项不填。

## 0. 结论

- 每局结束（通关或战败）自动生成两个文件：
  - `run_YYYY-MM-DDTHH-MM-SS_<骨架>.json`：结构化数据，供后续汇总；
  - 同名 `.txt`：已填好客观项的记录表，直接看即可。
- 不再需要手填时长、路线、战斗、成长、换装、商店、消耗品、遥测、首次落点用时。
- 手感、选路理由、难度、复玩意愿等主观项**按项目约定不记录**；作者认为有问题会直接反馈。
- 不写存档、不改数值/奖励/掉落/RNG、不弹界面。

## 1. 怎么开启

| 运行方式 | 是否自动记录 |
|---|---|
| 导出包（`ACT1 Demo` 预设，自定义特性 `act1_demo`） | 是，默认开启 |
| 编辑器 F6 / 控制台 | 默认关闭；命令行追加 `-- --runlog` 开启 |
| 自动化测试 / 冒烟 | 永不写文件（只在内存累计，测试结束丢弃） |

导出包直接双击即可；日志 bat 里的 stdout 会多一行 `RUNLOG|<txt 绝对路径>`。

## 2. 文件位置

`user://runs/`，Windows 实际路径：

```
%APPDATA%\Godot\app_userdata\Seek Dead Prototype\runs\
```

每次开局（确认开战）生成新文件名；同一秒重名自动加 `_1`、`_2` 后缀。
每场战斗结束和局末各落盘一次（战败/通关都不会丢整局数据）。

## 3. 记了什么

### 3.1 JSON 字段

| 字段 | 内容 |
|---|---|
| `mode` / `act` / `resolution` | 棋盘/线性、幕、窗口分辨率 |
| `board` | 骨架、模板、节点数、路径格数 |
| `loadout_start` / `loadout_end` | 开局与结束时武器组合 |
| `route` | 按顺序的节点 id / 类型 / 深度（含起点） |
| `battles` | 每场：序号、房型、房名、元素、敌方 HP/攻、结果、回合、玩家 HP |
| `growth` | 成长位选择：技艺、铭印（锋铸/调律 ×武器）、兜底「下一房对策」（护盾/金币/符号伤害），id + 中文名 |
| `weapon_changes` | 换武器：旧 → 新 + 来源（奖励/BOSS/商店/营地/宝箱/藏库） |
| `shop` / `camp` | 购买：名称、类别、价格 |
| `consumables` | 消耗品使用记录 |
| `special` | 宝箱/神龛/武器藏库：类型、节点、结果（开出什么/选了什么/跳过） |
| `first_pick` | 棋盘首次手动落点用时与节点（10 秒找落点） |
| `death` | 战败时的房/节点/HP |
| `result` / `duration_sec` | 通关或战败、整局时长 |
| `telemetry` | 现有 M1-06 遥测：回合、三连率、承伤、格挡、TTK、旋转、目标停中率、缓冲等 |

### 3.2 TXT 记录表

按现有 `记录表_每局.txt` 的客观字段排版，分六节：
本局概况 / 路线 / 战斗 / 成长与装备 / 遥测数据 / 10 秒找落点。
末尾明确标注「主观项不由本表记录」。

## 4. 不记什么

- 手感、难度是否合适；
- 为什么选这条路；
- 特殊格是否看懂、是否值得；
- 是否想再玩、最想改什么；
- 任何需要人判断的结论。

这些按 2026-11-08 项目决定由作者在认为有问题时直接口头反馈；AI 不代填。

## 5. 实现与边界

新增 `scripts/systems/run_journal.gd`（RefCounted，controller 持有 `_journal`）：

- `start_run()`：确认开战后记录模式/骨架/模板/初始配装；
- `note_board_shown()` / `note_first_pick()`：10 秒找落点计时；
- `note_node()`：路线与特殊格；
- `note_battle_start()` / `note_battle_end()`：战斗；
- `note_growth()` / `note_weapon_change()` / `note_shop()` / `note_camp()` / `note_consumable()` / `note_special()`：选择与获取；
- `finish()`：局末补全结果/时长/遥测并写文件。

挂点均为只读事件，不改结算顺序与 RNG：
`loadout_system.full_reset`、`board_screen`（展示/落点/前进）、`duel_controller`（开战/武器/营地/特殊格）、
`room_flow`（胜利/局末）、`shop_system`、`growth_system`、`consumable_system`。

写入策略：导出包或 `--runlog` 才落盘；目录 `user://runs` 与 `lobby_data.json` 完全分离。
测试默认不写文件；`run_smoke.bat` 已强制把 `user://` 重定向到 `%TEMP%\seek_dead_smoke_appdata`，
测试进程读不到也写不到真实存档。

## 6. 多局汇总

双击项目根目录的 `汇总记录.bat`（等价于 `python tools\run_summary_report.py`）：

- 默认读取 `%APPDATA%\Godot\app_userdata\Seek Dead Prototype\runs`，也可把别的 runs 目录拖进去；
- 生成 `runs\summary_<时间>.md`，控制台同时打印正文；
- 加 `--csv 明细.csv` 可额外导出逐局明细（Excel 直接打开）。

报告分六节：总览（局数/通关率/时长/承伤/停中率/首落点）· 按骨架 · 按模板 · 战败分布 · 逐局明细 · 换装与特殊格。
单组样本少于 3 局会标注「样本少」，只当方向看。

只读 `run_*.json`，不写存档、不改数值。中途退出没走到局末的局会显示为「未收口」，不计入胜率。
