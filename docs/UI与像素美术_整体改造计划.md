# Seek Dead · UI 与像素美术整体改造计划

> 状态：待执行，建议从 M0 启动  
> 制定日期：2026-10-29  
> 参考方向：用户提供的《He is Coming》截图，仅提取暗底、少色、剪影、线框等视觉特征，不复制其素材与界面  
> 核心决策：采用新的视觉语言，保留现有玩法、信息架构骨架和组件化工程基础；先做战斗样板，验收后再批量改造

---

## 1. 结论与改造原则

本项目适合转向“暗色地牢舞台 + 暖白线框 + 灰白玩家 + 红色敌人 + 少色像素图标”的风格。该方向与地牢、死亡、装备构筑题材匹配，也比厚涂、多色 AI 立绘更适合稳定量产。

本次改造遵循五条原则：

1. **换视觉规范，不换玩法**：不修改战斗结算、随机数、装备数值、房间流程和奖励逻辑。
2. **参考风格，不照搬游戏**：保留 Seek Dead 自己的三栏战斗结构、中央转轮和交互方式，形成独立的边框、图标与角色轮廓规则。
3. **先验证，再量产**：先用一个战斗界面和一组代表素材验证，未通过样板验收不生成整批资源。
4. **数据驱动、逐批替换**：缺少新素材时继续使用现有默认图或 emoji 回落，不允许半成品阻塞游戏运行。
5. **风格统一靠工程约束**：统一色板、尺寸、锚点、轮廓和后处理，不依赖 prompt 中反复写“保持风格一致”。

## 2. 现有基础与改造边界

### 2.1 可直接复用的基础

- 逻辑分辨率为 **480×270**，默认窗口 960×540，纹理过滤已为 NEAREST。
- 已有统一主题 `theme/battle_theme.tres`。
- 已有颜色与字号入口 `scripts/ui/palette.gd`、`scripts/ui/type_scale.gd`。
- 已有按钮、面板、转轮格、物品卡等组件场景。
- 战斗 HUD 已拆分为 `battle_hud.tscn` + `battle_hud.gd`，商店、奖励、整备、铁砧、元进度也已场景化。
- 敌人立绘已支持 `RoomData.art` 和 `art_scale`，缺少专属图时有默认图回落。
- 已有 48×48 小人、逐帧动画、调色板量化、contact sheet 验收等流程规范。
- 已有完整自动化回归入口 `run_smoke.bat`。

因此，本次**不需要重新进行 UI 架构重构**，主要工作是替换设计令牌、调整组件外观、精简战斗信息层级并建立可持续的素材生产链。

### 2.2 当前主要问题

- 背景、面板和按钮以蓝灰色为主，与新目标的暗紫褐、暖白线框不一致。
- 面板、卡片、转轮格各自保存样式，仍存在不少局部覆盖，换肤时容易出现遗漏。
- 主 HUD 常驻标题、10px 外框和装饰点占用本已紧张的 480×270 空间。
- 玩家、敌人、BOSS 与武器小人的色彩、细节密度和轮廓语言尚未统一。
- `knight1-5.png`、`bossbf.png` 属于既有厚涂噪点素材，不应继续作为新图风格参考。
- 现有文档依赖 `.workbuddy/` 中的个人后处理脚本；量产前需要把工具链固化为项目内可复现流程。
- 参考游戏的信息密度高于本项目，不能直接将其三栏尺寸和长文本压缩到 480×270。

### 2.3 不在本次范围内

- 不新增地图探索、装备拖拽、复杂场景灯光等新玩法。
- 不重做战斗状态机，不调整伤害公式和平衡常量。
- 不为每把武器制作独有攻击动画，继续采用动作原型复用。
- 不为 61 个房间配置机械地制作 61 张完全不同的敌人图。
- 不在样板验收前一次性重绘全部 200 件规划装备。

## 3. 目标视觉规范

以下色值是 **M0 候选规范**，需在 M1 实际画面验收后锁定，不应在未验证时直接批量替换全部资源。

### 3.1 色彩系统

| 语义 | 候选色 | 用途 |
|---|---|---|
| 主背景 | `#160D13` | 战斗与全屏界面的近黑暗紫褐底 |
| 面板背景 | `#1D1219` | 侧栏、卡片、抽屉，与主背景仅有轻微明度差 |
| 深描边 | `#3A222B` | 角色轮廓、图标暗部、内部隔断 |
| 主文字/主线框 | `#E2D7BD` | 标题、正文、关键面板边框 |
| 次级文字/次线框 | `#A99D89` | 描述、次要数值、非重点分隔线 |
| 玩家灰白 | `#B9B8B0` | 玩家与友方中性主体 |
| 敌人珊瑚红 | `#E35B50` | 敌人主体、伤害、危险和敌意意图 |
| 交互金 | `#D5A33D` | 主按钮、奖励、稀有强调、当前选择 |
| 生命绿 | `#A4BC4D` | HP、治疗和正向前缀 |
| 护盾蓝 | `#62A1C2` | 护盾、护甲和防御信息 |

颜色使用纪律：

- **红色只表达敌方、伤害和危险**，不与稀有度混用。
- **金色只表达可操作、奖励和重要选择**，不大面积用于纯装饰。
- 元素色继续服务元素克制，但需纳入统一色板并控制饱和度；元素身份不能只靠颜色，必须同时有图形差异。
- 面板背景不做高透明叠色，优先使用稳定的实色，避免不同界面上出现色偏。
- 建议全局核心色板控制在 32 色以内；普通敌人单图 2–4 色，武器小人单图不超过 8 色，特殊 BOSS 可适度增加但仍须入板。

### 3.2 线框、圆角与间距

- 所有组件保持方角，取消无功能圆角。
- 普通分隔与格子使用 1px 线框；当前选中、主操作、BOSS 重点框可使用 2px。
- 主线框采用暖白，次级容器使用较暗线框，避免所有面板同时高亮。
- 以 4px 为基础间距单位；紧凑处可用 2px，面板内边距优先 4–6px。
- 铆钉、角饰只用于一级框架和稀有奖励，不给每个小格子添加装饰。
- 移除主 HUD 的 10px `DeviceFrame` 厚框和无功能装饰点，改为薄边框，将空间还给战斗内容。
- 保留现有容器和锚点方案，不用绝对坐标重排整套 UI。

### 3.3 字体与排版

- 保留 `VonwaonBitmap-12px` + `zpix` 中文回落，不为追求参考图效果更换不清晰的中文字体。
- 继续优先使用现有字体已缓存的 9/10/16px 档位，禁止随意引入非整数缩放字号。
- 战斗内删除常驻“Seek Dead · 老虎机对决”产品标题；产品名留给开始、结算或试玩说明界面。
- 正文优先短句，常驻面板最多显示结论；完整机制说明放入 tooltip。
- 数值使用“图标 + 数字”结构，重要 HP、攻击、意图不得仅靠 9px 弱文字表达。
- 装饰性标题字体只能用于英文短标题，不能扩展到中文正文和战斗日志。

### 3.4 图标规范

| 类型 | 源文件规格 | 规则 |
|---|---|---|
| 转轮符号、状态、属性 | 16×16 | 独立绘制小图标，不能由 48×48 直接缩小 |
| 物品栏、商店小图标 | 24×24 | 1–2 个主色，保留清晰外轮廓 |
| 武器小人、卡片主图 | 48×48 | 与角色规范一致，透明背景 |
| 普通 UI 线框 | 9-slice 或组件样式 | 1px 硬边，禁止双线性缩放 |

- 同组图标统一视觉重量、描边、留白和透视，不混用正视、侧视和等距视角。
- 物品图标优先描绘“物体本身”，不添加复杂场景、光晕和文字。
- 符号图标必须同时表达形状与系别，避免仅换色的六个相同轮廓。

### 3.5 角色与 BOSS 规范

| 对象 | 建议规格 | 视觉规则 |
|---|---|---|
| 玩家 | 48×48 | 灰白主体、深色描边，装备可用少量元素强调色 |
| 武器小人 | 48×48 | 保留角色感与剪影差异，每图最多 8 色，系别色作为局部身份色 |
| 普通敌人/精英 | 48×48 | 红色主体 + 暗部，精英通过轮廓附件和底座区分，不只放大或换色 |
| BOSS | 优先 64×64，最终 BOSS 可试 96×96 | 大体型、强剪影、少量标志性结构；实际显示按舞台空间验收 |
| 投射物/命中特效 | 8×8～16×16 | 与角色分离，按元素和动作原型复用 |

- 玩家、敌人和武器小人统一像素密度，不使用非整数缩放制造大小差异。
- 普通敌人统一红色系，但必须能仅凭纯黑剪影区分；颜色不能掩盖轮廓设计失败。
- BOSS 的辨识度依次来自：**外轮廓 → 标志性部件 → 姿态 → 少量颜色**，不来自噪点和纹理。
- 不为每个敌人制作完整动作集。优先静态图 + 代码位移/受击闪白/死亡效果；确有触发点和收益时再补帧。
- 受击反馈由“红闪”改为“暖白闪或明暗反相”，避免红色敌人受击时反馈不明显。

### 3.6 背景与演出

- 第一阶段不做详细地牢背景，使用纯色舞台、简单地面接触影和极少量环境符号。
- 转轮始终是中央主要交互物，不能被大型 BOSS、粒子或装饰框遮挡。
- 保留现有 `BattleAnimator` 和动画时长约束，不为换风格改变战斗结算节奏。
- 命中、暴击、破甲和击杀优先使用短促位移、1–2 帧图形特效和飘字，不引入高噪点全屏粒子。
- 所有演出随机继续使用局部 RNG，不消耗全局种子流。

## 4. 各界面改造方向

### 4.1 战斗 HUD：第一优先级

保留“左侧玩家 / 中央舞台与转轮 / 右侧敌人”的可用结构，进行以下调整：

- 顶栏压缩为房间、回合、金币与间歇操作，不重复显示能从其他位置读到的信息。
- 左栏以武器、护符、技能和消耗品图标为主，减少分类标题与重复emoji。
- 中央保持玩家与敌人对峙，转轮和 SPIN 位于其下方；BOSS 增大时优先压缩空白，不挤压转轮。
- 右栏优先显示敌人名、HP、护甲和下一意图；元素、弱点、抗性与状态按战斗相关性分组。
- BOSS 长机制说明不常驻整段显示，右栏保留一行当前阶段结论，完整规则通过 tooltip 查看。
- 伤害日志保持辅助地位，不用大段文字争夺中央视觉焦点。
- 下一房预告、商店和下一房按钮的可用状态必须同时通过亮度、边框和文字表达，不能只换颜色。

### 4.2 整备界面

- 保留当前分类、勾选和配装逻辑，只统一卡片、选中框、图标和背景。
- 五个类别小人可保留功能定位，但需按新规范重绘或量化，不与新角色形成两套风格。
- 选中状态采用“金色框 + 明确标记”，不再仅依靠绿色底。
- 卡片默认展示名称、主图与核心效果，详细说明仍由 tooltip 承担。

### 4.3 商店与铁砧

- 商店继续采用右侧抽屉，不改回全屏强制商店。
- 价格、可购买、买不起和已售出使用不同图形状态，禁止只用红绿区分。
- 铁砧以暗底和有限锻造金橙为强调，不另起一套高饱和 UI。
- 抽取、保底和返还信息按优先级排版，避免所有说明同时常驻。

### 4.4 奖励、元进度与结算

- 奖励继续采用居中卡片弹层，三个选项使用同一组件与同一图像规格。
- 稀有奖励可以增加角饰，但不改变卡片尺寸，避免选项跳动。
- 失败、通关和元进度界面沿用同一色板与按钮语义，形成完整闭环。
- 产品标题和装饰性排版集中在这些非实时界面，战斗 HUD 保持克制。

### 4.5 Tooltip 与战斗日志

- Tooltip 使用实色暗底、暖白细边框和固定最大宽度。
- 先显示名称与核心结果，再显示条件和细节；避免一打开就是整段公式。
- 中文 9px 在实际窗口中若无法稳定阅读，应删减文字或扩大 tooltip，而不是继续缩字。
- 日志与 tooltip 可以保留辅助emoji，但主要交互和主视觉图标最终应由项目自有像素图标替代。

## 5. 素材清单与复用策略

### 5.1 资产分层

| 层级 | 内容 | 生产方式 |
|---|---|---|
| UI 基础套件 | 面板、按钮、卡片、转轮格、tooltip、选中/禁用状态 | 代码 Theme + 少量原创九宫格/角饰 |
| 战斗语义图标 | HP、攻击、护盾、金币、状态、意图、元素、特殊符号 | 按图标族生成，统一后处理 |
| 武器与物品 | 武器小人、技能、护符、消耗品图标 | 按类别分批，缺图使用既有回落 |
| 普通敌人 | 以实际 archetype/轮廓族为基础，而非按房间数重复生产 | 基础剪影 + 元素/精英变体 |
| BOSS | 当前 13 个 BOSS 各自建立标志性轮廓 | 逐个设计、逐个验收，不做同模换名 |
| 玩家与演出 | 玩家核心动作、通用命中/死亡/投射物 | 复用动作原型和代码演出 |

### 5.2 数量口径

- 装备规划目标为 200 件，但美术必须与内容落地同步，不能提前为尚未定稿的物品大量出图。
- 当前 61 个房间配置不等于 61 个独立角色；先建立“视觉 ID → 房间资源”的映射，复用同族敌人。
- 当前 13 个 BOSS 应有独立轮廓；同族变体可以共享部件，但不能只替换颜色。
- ACT1 Demo 的 50 件白名单内容、实际出场敌人和 4 个 BOSS 是第一个完整素材闭环。

### 5.3 旧素材处理

- `knight1-5.png`、`bossbf.png` 仅保留为历史动画与尺寸参考，不再作为风格锚点。
- `char.png` 在样板阶段转为“结构与动画参考”；是否继续作为角色造型基准，由新玩家样板验收结果决定。
- 旧图不立即删除。新图接入并通过 F6 后，再按批次替换，保留可回退版本。
- 已验证可用的图标和 Kenney 组件可作临时占位，但最终需统一轮廓、色板和视觉重量，并保存许可证记录。

## 6. AI 美术量产流程

### 6.1 先锁定生成后端

量产前进行一次小规模后端对比，不直接绑定某个 MCP 或在线服务：

1. 准备同一组 12 张描述卡：武器小人 4、普通敌人 4、BOSS 4。
2. 在两个可实际访问的后端分别生成，每题保留 2–3 个候选。
3. 使用相同后处理，拼成 contact sheet 盲评。
4. 比较剪影成功率、透明背景、色数、同角色多帧一致性、返修率、单张成本和生成耗时。
5. 选择一个主后端和一个备用后端后才进入批量生产。

候选可包括 Retro Diffusion、PixelLab、可稳定联网的生成 MCP 或本地 ComfyUI；选择以实测结果为准，不以工具宣传为准。

### 6.2 每个资产的输入包

- 一句身份：它是什么。
- 一句轮廓：最远处也能识别的 1–2 个特征。
- 所属类别与元素：决定色系和图标语义。
- 指定画布、朝向、锚点和色数。
- 已批准的项目自有参考图：同类别、同动作或同轮廓族。
- 负面约束：无抗锯齿、无渐变、无厚涂、无噪点、无复杂背景、无额外肢体、无文字。

Prompt 描述具体视觉属性，不把“模仿某游戏”作为唯一风格约束。第三方截图用于研究布局与配色，不直接充当项目自有训练素材库。

### 6.3 静态资产生产链

```text
描述卡
  → AI 生成 2–4 个候选
  → 1×剪影筛选
  → 去背景/透明化
  → 整数倍归一到目标画布
  → 项目色板量化
  → 自动规格检查
  → 同批 contact sheet 目视验收
  → Godot 实机验收
  → 入库并绑定资源
```

任何 AI 直出图都不得跳过规格检查和实机验收直接入库。

### 6.4 动画生产链

- 先验收 idle 站立帧，再生成同角色其他动作。
- 同角色全部动作使用同一会话/种子族，后续动作必须附带已批准 idle 帧作为参考。
- 保持既有 48×48、脚底贴底、水平居中、统一朝向和帧命名。
- 跨动作站立帧身体宽高偏差继续以 ±8% 为报警线，帧间脚底/中心偏移超过 1px 报警。
- 动作结构失败时回生成端重做，不用非整数缩放、涂抹或手工补像素掩盖。
- 攻击动作继续受 0.35 秒战斗窗口约束，动画只由演出层读取。

### 6.5 工具链固化

将量化、透明化、锚点归一、规格检查、contact sheet 等能力整理到项目内可复现的工具目录，目标为 `tools/art_pipeline/`：

- 明确 Python/Pillow 等运行依赖与命令入口。
- 输出机器可读检查结果和总览预览图。
- 检查尺寸、RGBA、透明背景、板外色、色数、包围盒、帧间对齐和命名。
- 原始 AI 图、候选图与最终入库图分目录保存，原始大文件不混入游戏资源目录。
- 保存生成后端、模型/版本、种子、prompt、参考图批次和后处理版本，保证问题可追溯。

### 6.6 批次纪律

- 武器每批 5–8 件，与本批装备 `.tres` 同步交付。
- 普通敌人按轮廓族分批，每批先做一个基准，再做变体。
- BOSS 每次只推进 1 个，完成“剪影 → 实机 → 机制匹配”后再做下一个。
- 每批都要重跑自动化回归；新增装备仍需执行平衡探针的 ±30% 警觉线检查。
- 每批独立提交，素材、资源绑定和文档进度一起交付，不积累无法追踪的大批临时图。

## 7. 分阶段执行路线图

### M0 · 基线记录与规范锁定（P0）

**目标**：知道改什么、如何验收，并保留可对比基线。

- 截取当前战斗、整备、商店、奖励、铁砧、结算界面。
- 盘点所有主图标、角色、敌人、BOSS 与回落路径，建立资产映射表。
- 确认候选色板、字体、线宽、间距和图标规格。
- 核实并整理 AI 后处理工具链。
- 选择样板内容：1 个玩家、1 把武器、1 个普通敌人、1 个 ACT1 BOSS。

**出口**：规范表、资产清单、当前截图、样板描述卡齐备。  
**不做**：批量生成、不改战斗逻辑、不删除旧素材。

### M1 · 战斗垂直样板（P0）

**目标**：用最小完整画面证明方向可行。

- 改造 `battle_theme.tres`、`palette.gd` 和核心组件外观。
- 调整战斗 HUD 薄框、顶栏、中央舞台与信息层级，保留三栏和转轮主交互。
- 接入样板玩家、武器小人、普通敌人和 BOSS。
- 接入一组足以验证转轮辨识度的像素符号图标。
- 对红色敌人验证暖白受击反馈，对 BOSS 验证舞台尺寸和右栏说明。
- 生成改造前后对比图与一张风格 contact sheet。

**验收门槛**：

- 480×270 下无裁切、重叠、非预期滚动和文字溢出。
- 960×540、1440×810、1920×1080 整数放大下像素清晰。
- 1280×720 下至少保证布局可用，无非预期遮挡。
- 玩家、普通敌人、BOSS 只看剪影即可区分。
- 转轮转动与停止时图标可辨，SPIN 和下一意图是明确视觉重点。
- 中文正文、HP、价格、tooltip 在实机窗口可读。
- `run_smoke.bat` 8/8 通过。

**只有用户确认 M1 样板后，才进入全面改造。**

### M2 · 全界面视觉统一（P1）

**目标**：所有已有界面使用同一套视觉语言。

- 按战斗、整备、奖励、商店、铁砧、元进度/结算的顺序逐屏改造。
- 收敛 `ui_button`、`ui_panel`、`symbol_cell`、`item_card` 的局部样式覆盖。
- 统一卡片图标位、选中态、禁用态、稀有度和 tooltip。
- 每完成一屏即进行 F6 验收，不把六屏问题积到最后。
- 更新 `type_scale.gd`、`palette.gd` 和相关文档中描述旧视觉的注释。

**出口**：全流程截图无旧蓝灰主题残留，无功能回退，自动化回归 8/8 通过。

### M3 · ACT1 完整美术闭环（P1）

**目标**：优先让可试玩内容完整，而不是平均推进三幕。

- 完成 ACT1 Demo 白名单 50 件内容所需的主图标/小人。
- 完成 ACT1 实际出现的普通与精英敌人视觉映射。
- 完成冰封铁瓮、碎裂石像鬼、酸蚀恶鬼、茧居石雕 4 个 BOSS。
- 补齐 ACT1 使用的状态、意图、元素和奖励图标。
- 完成一轮 ACT1 实机检查，记录缺图、错图、重复感与可读性问题。

**出口**：ACT1 主流程无厚涂历史图和临时默认敌人突兀混用，具备试玩展示一致性。  
**联动**：本阶段可与 ACT1 Demo 配置和导出工作并行，不互相阻塞。

### M4 · 全量内容与装备铺量同步（P2）

**目标**：新内容落地即带合格美术，逐步替换存量。

- 按“Act2 → Act3 → 真最终 BOSS”补齐敌人与 BOSS。
- 新武器、技能、护符、消耗品按 5–8 件批次同步出图。
- 每批同时更新资源绑定、资产映射、平衡探针与回归结果。
- 对复用过多的敌人族补充轮廓附件和姿态，不靠随机换色制造伪多样性。
- 每幕结束做一次全角色 contact sheet 审核，清理风格漂移。

**出口**：所有正式启用内容均有合规主视觉；回落只用于开发中的临时内容。

### M5 · 表现打磨与最终收口（P3）

**目标**：在风格稳定后提升质感，不用特效掩盖素材问题。

- 挂接并验收现有击杀溶解等已具备但尚未使用的演出。
- 增加少量通用破甲、暴击、状态与 BOSS 阶段切换特效。
- 检查所有场景的焦点、悬停、禁用和键盘操作状态。
- 整理最终风格规范、许可证、源文件和生成记录。
- 清理已完全替代且无回退需要的旧素材，单独提交。

**出口**：视觉、交互、演出和文档一致，形成后续内容可直接复用的生产规范。

## 9. 验收体系

### 9.1 每张素材的自动检查

- 尺寸、RGBA、透明背景、文件命名正确。
- 所有颜色属于批准色板，单图色数不超过对应档位。
- 无抗锯齿过渡色、非预期背景和大面积噪点。
- 角色锚点、脚底和帧间对齐符合规范。
- 图标由正确源规格制作，不存在 48→16 等直接缩小。
- Godot 使用 NEAREST，资源路径和 `.tres` 绑定有效。

### 9.2 每批素材的人工检查

- 1×大小可辨，不只在 5×放大图中好看。
- 转为纯黑剪影后仍能识别角色和主要装备。
- 同批接触表中像素密度、线条、比例和色彩一致。
- 图标在转轮运动、悬停、禁用和匹配角标同时出现时仍可读。
- BOSS 外观能呼应机制，例如铁瓮的封闭/护甲感不能只靠名称表达。
- 实机检查玩家、敌人、背景、危险提示之间有足够的明度与色相区分。

### 9.3 每个里程碑的工程检查

- 执行 `run_smoke.bat`，要求 8/8 全部通过。
- F6 完整走通整备 → 战斗 → 奖励 → 商店/间歇 → BOSS → 结算。
- 核查鼠标、空格、焦点、tooltip、替换购买和消耗品使用没有因布局改变失效。
- 对比改造前后截图，确认没有文字溢出、节点遮挡和异常最小尺寸。
- 视觉改动不得改变同种子战斗结果，不得消耗全局 RNG。

### 9.4 整项改造完成定义

- 所有正式界面使用同一设计令牌与组件状态。
- 所有正式启用内容具有合规主图或图标，不再依赖厚涂历史图作为主视觉。
- 普通敌人、武器小人和 BOSS 可按文档稳定批量新增。
- ACT1 至 ACT3 的实机画面均完成一次集中 F6 验收。
- 生产工具、生成记录、素材映射和许可证可追溯。
- 自动化回归全绿，且无已知的严重可读性或交互回退。

## 10. 风险与回退策略

| 风险 | 早期信号 | 处理与回退 |
|---|---|---|
| 全部红色敌人导致趋同 | contact sheet 中只能靠名字区分 | 回到剪影重设计；减少同族数量，不增加颜色噪声 |
| 480×270 信息过载 | 文字溢出、tooltip 过长、转轮被挤压 | 减常驻文案、恢复信息分组；不通过继续缩字解决 |
| AI 批次风格漂移 | 色数、比例、描边和像素密度明显变化 | 停止该批，回到已批准参考包；不继续扩大生成量 |
| 动画跨动作变形 | 宽高偏差超过 ±8%、脚底跳动 | 同批重生成，不在后处理中非整数缩放 |
| 新风格与元素色冲突 | 弱点、危险、稀有度难以区分 | 保留颜色语义并增加形状/图标编码，重新审查色板 |
| 工具或网络不可用 | 后端无法稳定生成、成本不可控 | 使用已验证备用后端；暂缓量产，不影响现有游戏运行 |
| 改造范围拖垮内容进度 | 长时间只做旧图替换，没有可玩增量 | 以 ACT1 闭环优先，新装备与美术同步，旧图按批替换 |
| 与参考作品过于相似 | 边框、图标、角色或布局可被误认为原作素材 | 使用自有轮廓和组件规则，不复制原作资源与具体设计 |
| 换肤引入功能回退 | 节点路径失效、按钮状态错误、场景解析失败 | 每屏独立提交；自动回归 + F6；按组件或提交回退 |

## 11. 推荐执行顺序与立即行动

推荐顺序为：

```text
M0 规范与基线
  → M1 战斗样板及用户验收
  → M2 全界面统一
  → M3 ACT1 美术闭环（与 Demo 工程并行）
  → M4 随装备铺量扩展全三幕
  → M5 演出与最终收口
```

启动时只做以下五件事：

1. 建立当前界面截图与资产映射基线。
2. 锁定 M0 候选设计令牌和样板描述卡。
3. 实测两个可用 AI 后端，选择主备方案。
4. 制作一个完整战斗样板，而不是先生成几十张角色图。
5. 样板通过后再更新既有像素管道文档，并开始 ACT1 批量生产。

**最重要的控制点：M1 未通过，不进入量产；任何一批未通过实机验收，不继续扩大下一批。**
