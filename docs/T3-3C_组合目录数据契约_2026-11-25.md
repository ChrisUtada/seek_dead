# T3-3C · 组合目录数据契约（2026-11-25）

> 性质：C 轮前置——纯只读数据契约。不写 UI、不改结算、不加 RNG。
> 实现：`scripts/battle/combo_catalog.gd`（`class_name ComboCatalog`，全 static，无状态）

## 1. C 轮面板接口约定

面板**只消费** `ComboCatalog.build_rows(pattern_system, loadout_paths, tag_of, last_acc)` 的输出，**不直接读 acc**。

```gdscript
static func build_rows(pattern_system, loadout_paths: Array, tag_of: Callable,
        last_acc: Dictionary) -> Array[Dictionary]
```

## 2. 字段表（每行固定 8 字段）

| 字段 | 类型 | 来源 |
|---|---|---|
| id | String | `PatternData.id` / G 系常量 id |
| name | String | `PatternData.name` / G 系常量名 |
| group | String | 见 §3 分组映射 |
| priority | int | `PatternData.priority`；G 系固定 0 |
| unlocked | bool | **直接复用** `PatternData.unlocked(loadout_paths, tag_of)`（`pattern_data.gd:60-88`）；G 系恒 true |
| matched_now | bool | 只读 `last_acc`：`pattern_weapon` / `pattern_skill` / `pattern_signature` / `patterns_universal` 的 id 集合；G 系同看通用位 |
| condition_text | String | `PatternMatcher.describe_condition()` 逐条件拼接（` + `）；G 系手写固定描述 |
| contribution_text | String | 从 `last_acc["lines"]` 按牌谱名匹配，取不到留空 |

## 3. 分组映射（按 StepA §D 裁决；与实际资源对照）

| group | 映射 | 实测行数 |
|---|---|---|
| base | G01/G02/G03（pattern_matcher.gd:21-23 常量，**合成只读行，不迁资源**） | 3 |
| main | `track == "weapon_attack"`（W01–W07） | 7 |
| aux | `track == "skill"` 或 **`"skill_support"`**（T01–T03 实际用后者） | 3 |
| signature | `track == "signature"`（11 sig_* + s02） | 12 |
| universal | 其余（当前 0） | 0 |

**与工单写法的差异（按实际资源填）**：工单 B1 写「21 个 PatternData + 3 G = 24 行、signature 11」，那是 W07 入库前的数字；当前仓库有 **22 个 PatternData**（含 W07），故 **25 行**、main 7、signature 12。工单的 `aux ← track == "skill"` 与实际 `skill_support` 不符，目录同时兼容两者。

## 4. acc 中实际可用的键（按代码事实）

`combat_system.gd` 的 `_apply_patterns` 写入：
- `pattern_weapon`（String，`:461`）
- `pattern_equipment`（String，兼容键，`:462`）
- `pattern_signature`（String，`:463`）
- `pattern_skill`（String，`:491`）
- `patterns_universal`（Array[PatternData]，`:450`）
- `pattern_match`（Dictionary，`:444`）：结构 `{"ok": bool, "triple_kind": String, "patterns": [{"id": String, "name": String}, ...]}`；G01/G02/G03 命中从这里读取，可能为空字典或缺 `patterns` 键，契约层安全跳过
- `lines`（Array[String]，`:231` 等）

**没有** `charge_points` 键（那是 `_ctrl` 字段），目录不读它。

## 5. 只读保证

`build_rows()` 及其私有 helper 只做：遍历 `pattern_system.all_patterns()`、调用 `p.unlocked()`（纯函数）、读 `last_acc`、调用 `MATCHER.describe_condition()`（纯函数）。**不读写** `enemy_hp` / `enemy_status` / `charge` / RNG，不调用任何改状态方法。测试验证调用前后 `_loot.seed_value()`、`enemy_hp`、`enemy_armor` 完全不变。

## 6. 已知修正（2026-11-25）

- **G 系 `matched_now` 曾恒 false**：原因是 `_matched_ids()` 只读 `pattern_weapon` / `pattern_skill` / `pattern_signature` / `patterns_universal`，未读 `acc["pattern_match"]["patterns"]`。已修：从该列表取每个 `{"id","name"}` 的 id 并入命中集合；G01/G02 可同时命中（同源刻与同族刻互不排斥），资源行不受影响。改前红：`FAIL G01 命中（来自 acc.pattern_match）`、`FAIL G01+G02 同时命中（同源+同族并存）`、`T3CCAT|RESULT FAIL (checks=20 fails=2)`；修复后绿。
- **条件文本折叠**：相邻相同描述合并为「描述×N」，W07 → `blade×1 + flame×2`；无重复时保留原描述（W01 三条仍用 ` + ` 拼接）。
