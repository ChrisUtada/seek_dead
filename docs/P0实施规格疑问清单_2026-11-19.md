## 1. 🔴 根本疑问：生成范式要"重构"还是"改造"？（最重要）

**规格假设**（§2.1、§3、§4）：新生成器 = 类别权重抽取 + 槽位倾向（Slot A/B/C）+ 动态重分配 + 类别替补。

**当前代码实际**（`draft_composer.gd`）：
```
compose()
  → _eligible()        硬过滤（定义合法/满血/规则）
  → _compose_samples() 采样 DRAFT_SAMPLES=6 组
  → _sample_group()    按稀有度权重抽每组3张
  → _draft_score()     对6组评分（协同W_PAIR_SYNERGY / 稀有度张力W_TENSION /
                       同标签惩罚W_SIMILARITY / 随机W_RANDOM），选最高分组
  → _weighted_index()  加权选组
```
注意代码注释（draft_composer.gd:65）：**"采样只看稀有度，不看情境评分；评分仅在 debug 下计算用于展示"**——即当前是"稀有度采样 + 选组"，规格要的是"类别权重 + 槽位倾向"。

**疑问**：
1. 这是要**整体替换** `_compose_samples`/`_draft_score`/`_sample_group` 这一套？还是保留评分选组、在其上叠加类别权重？
2. 规格 §4.4 说"P0不实现复杂评分模型，用 tags/effect_family/类别做规则检查"——但现有代码**已经有**评分模型（虽然已降级为 debug 展示）。是删除它，还是保留但不用？
3. 现有 `RewardEvaluator`（`context_rule`/`synergy_rule`）在 debug 里仍在跑（`draft_composer.gd:77`）。规格完全没提它的去留——继续保留会不会与新类别体系双轨？

**为什么重要**：这是 P0.1 的核心工作，方向不清会导致返工。建议明确写一句："P0 是否废弃现有评分选组，全面改为类别权重+槽位倾向？"

## 2. 🔴 数据字段冲突：规格的字段名与 RewardDefinition 不一致

**规格 §9.2 必须字段**：`id` / `category` / `title` / `description` / `effect_id` / `effect_params` / `tags` / `effect_family` / `stack_policy` / `stack_limit` / `enabled` / `conditions`

**当前 `reward_definition.gd` 实际字段**：
| 规格字段 | 当前对应 | 状态 |
|---|---|---|
| `id` | `id` | ✅ |
| `title` / `description` | `name` / `desc` | ⚠️ 命名不同 |
| `category` | ❌ 无（只有开放 `tags`） | 🆕 需新增 |
| `effect_family` | ❌ 无 | 🆕 需新增 |
| `effect_id` / `effect_params` | 在 `effects: Array[Dictionary]` 里，形如 `{"effect_id":"heal","params":{"pct":0.35}}` | ⚠️ 规格写成了顶层字段 |
| `stack_policy` / `stack_limit` | `stack_rule: StackRule` 枚举 + `max_stack: int` | ⚠️ 语义近似但不同 |
| `enabled` | ❌ 无（靠 `validate()` + `unlock_rule`） | 🆕 需新增 |
| `conditions` | `eligibility_rule` / `context_rule` / `synergy_rule` / `unlock_rule` / `offer_rule`（字符串键名，映射到 RewardEvaluator） | ⚠️ 语义不同 |
| `rarity` | `rarity` | ✅ |
| `tags` | `tags` | ✅ |

**疑问**：
1. 规格 §9.1 的 JSON 示例用了顶层 `effect_id`/`effect_params`，但当前是 `effects` 数组（支持多效果）。P0 是否改为单效果顶层？还是会破坏现有 11 张签名卡 + 全部 seed 奖励（都是数组结构）？
2. `stack_rule` 当前是枚举（NONE/…），规格要字符串策略 `unique`/`stack_limited`/`replace`/`repeatable`——是新增字段还是改枚举？改枚举要同步所有 `.tres`。
3. `conditions` 用字符串规则键（现有模式）还是结构化数组（规格示例）？如果用结构化，RewardEvaluator 怎么办？
4. **兼容性疑问**：新增字段后，现有 `resources/rewards/defs/` 下所有 `.tres` 是否需要批量补字段？规格 §11.3 提到存档版本迁移，但没提**奖励资源文件**的迁移。

**建议**：在 §9 增加一张"规格字段 ↔ 现有字段映射表"，明确哪些重命名、哪些新增、旧资源如何兼容。

## 3. 🟡 技艺保底语义与当前实现不一致

**规格 §6.2**：`reward_room_count_since_skill_offer`——"距上次技艺展示已过几房"，满 3 房且有合法技艺则强制注入，展示后归零，自然出现也归零。是**滚动计数**。

**当前实现**（`growth_system.gd:109`）：
```gdscript
var guaranteed := rooms_settled <= PERK_GUARANTEE_ROOMS and perks_offered == 0
```
是"**开局前 3 房内只要提供过 1 次就永久关闭保底**"，不是滚动的"每 3 房保底一次"。

**疑问**：
1. 以哪个为准？如果按规格改成滚动计数，玩家可能整局反复见到技艺（每3房一次），与"技艺是少量战术支援"（总纲 §11）的定位可能冲突。
2. 规格说"取消独立15%注入，由类别权重控制"，但当前 15% 是"保底后每房概率"——如果技艺并入 8% 类别权重，那"前3房保底"的**滚动 vs 一次性**差别就很重要了。
3. 规格 §6.1 说"前3个有效奖励房间至少出现一次"——字面像一次性；§6.2 的计数定义又像滚动。**规格内部这两句是否矛盾？**

**建议**：明确二选一：(a) 仅开局前3房一次性保底；或 (b) 全局每3房滚动保底。写清楚。

## 4. 🟡 符号改造的 `symbol_id` 与实际 `resource_path` 不对齐

**规格 §9.1 示例**：`"effect_params": {"symbol_id": "symbol_x", "weight_delta": 1}`

**当前代码**（`battle_math.gd:62`、`reward_system.gd:26`）：
```
run_symbol_bonus: Dictionary  # resource_path -> 额外权重

```

**疑问**：`symbol_id` 就是符号 `.tres` 的 `resource_path` 吗？还是有独立 ID？规格里要"开发核对后配置"，但生成器候选筛选（§5.2"目标符号不存在则过滤"）依赖这个键——如果键定义错了，整个符号改造类别的过滤会失效。**建议在 §8.1 明确写"symbol_id = res://resources/symbols/*.tres 的 resource_path"。**

## 8. 规格本身措辞需澄清的小歧义

1. **§1.1 "奖励状态存储：Run内状态可保存、可恢复"** vs **§11.1 存档字段**：当前项目有 Run 存档吗？如果有，是哪个文件（`battle_state.gd` 有 `run_symbol_bonus` 等快照字段）——规格没点名，实现时会找错地方。
2. **§4.2 步骤9-10**（先生成3项→检查保底→替换一个为技艺）与 **§6.3 保底注入方式**（Composer初步生成→注入技艺）重复描述了同一件事，但是否是**同一流程**？步骤编号不同（4.2 是12步，6.3 是6步），容易造成两套实现。
3. **§14.1 "技艺保底计数达到3"** 与 §6.1 "前3个有效房间" ——若采用"一次性保底"，测试断言应写"第3房时"而非"计数达到3"（后者暗示滚动）。
4. **§3.1 签名类别权重5但P0不接入** + **§3.2 重分配** ——规格已明确处理（签名权重重分配），✅ 无疑问。但**技艺类别8%**与保底的关系（保底强制注入时是否绕过8%权重）在 §4.2/§6 里没明说——应该是绕过的（保底优先），建议写死。
5. **§8.1 "P0可以先实现其中6项；如果符号效果尚无通用接口，先实现权重强化类"** ——当前代码确认有 `run_symbol_bonus` 权重通道，但**没有符号效果的通用 Run 级修改接口**（状态伤害/防护/资源强化要各改结算分支）。所以 §8.1 的 `sym_effect_01~04` 实际上 P0 大概率做不了——建议规格里直接标注"sym_effect_* 为 P1+，P0 只做 sym_weight_*"，避免实施时卡住。
