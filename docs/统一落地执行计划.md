## 3. 统一目标与交付顺序

### 3.1 近期目标

首先交付一个可供真人完整体验的 **ACT1 垂直切片**：

- 核心奖励和收藏规则真实有效。
- 玩家能看懂构筑对应的实际转轮带。
- 角色与武器在一幕内都有可见成长。
- 武器以统一图标呈现，敌人与 BOSS 形成新像素风格。
- 可通过独立 Demo 配置导出并交给测试者。

### 3.2 中期目标

将 ACT1 验证过的成长、视觉与奖励机制扩展到完整三幕，同时完成装备 200 件与对应美术，不为凑数复制同质内容。

### 3.3 长期目标

以生涯成就、图鉴、横向铸式、身世和 GAME+ 提供长期复玩目标；永久成长以横向选择为主，不形成无限数值义务。

### 3.4 里程碑关系

```text

  ├─→ M1 核心系统修复 ─→ M2 ACT1 成长样板 ─┐
  └─→ M3 UI/美术战斗样板 ──────────────────┤
                                             ↓
                                  M4 ACT1 Demo 完整交付
                                             ↓
                                  M5 完整三幕系统与成长
                                             ↓
```

**M1 与 M3 可并行；M4 必须同时等待 M2、M3 验收通过。**

- 不允许通过卖出低于双武器下限绕过规则。

重点文件：

- `scripts/systems/reward_system.gd`
- `scripts/battle/duel_controller.gd`
- `scripts/systems/shop_system.gd`
- 奖励与替换相关 UI

验收：

- 正常强制双武器流程中，BOSS 主题武器能够出现并替换。
- 普通房/精英动态位的武器奖励按各自幕规则可达。
- 信物、铁砧点兜底与现有主题权重不回退。

> ✅ **完成记录（2026-10-30）**：
> - **候选不再被槽位前置拦截**：`roll_rewards` / `roll_elite_rewards` / `roll_boss_rewards` 移除「武器槽有空位」条件；幕一教学期仍不出构筑武器。
> - **展示前预确定**：武器卡生成时按获取权重抽定具体武器，写入 `reward_system.choice_payloads`（与 `reward_choices` 按 index 对齐）；卡片显示「武器 · 名字」，确认后不再二次随机。奖励信号改为 `reward_chosen(id, index)`。
> - **满槽替换**：选择武器奖励 → 复用 `hud.request_weapon_replace` 弹层 → `duel_controller._apply_reward_weapon_replace`；旧武器移出配装，新武器入槽。BOSS 战利品走同一替换路径。
> - **收藏写入**：奖励 / BOSS / 替换获得的新武器统一经 `remember_weapon()` 写入 `meta.owned_weapons`。
> - **卖出下限**：沿用 `loadout_min = 2` 拦截，并纳入回归。
> - **回归**：新增 `tests/m1_reward_reach_test.tscn`（19 断言，覆盖池闸门 / 预确定 / 空槽授予 / 满槽替换 / BOSS 主题武器 / 精英动态位 / 卖出下限），接入 `run_smoke.bat` 第 9 套；全 9 套绿（exit 0）。

### M1-02 奖励结果前置确定

- 符号灌注在卡片展示前确定具体符号和实际格数变化。
- 武器、消耗品奖励在卡片展示前确定具体物品。
- 玩家确认后不再进行第二次随机。
- 无法产生有效变化的灌注不进入候选，不使用“宁可死 roll”的兜底。
- 卡片明确展示实际结果和替换要求。

验收：玩家能在选择前准确比较三个结果。

> ✅ **完成记录（2026-10-30）**：
> - **符号灌注前置确定**：`RewardSystem.symbol_infusions()` 只收集「灌注后转轮带格数真的变多」的 damage 符号，候选在生成奖励卡时抽定具体符号，并把 `before/after` 真实格数写进 payload（卡片显示「转轮带 3 格 → 4 格」）；应用时按 payload 生效，不再二次随机。旧的「宁可死 roll」兜底与「回退全符号」分支已删除。
> - **格数口径单一来源**：新增 `ReelSystem.cells_for()`（权重档位 2/3/4 + 非 damage 稀有封顶 + 共享来源突破），`build_strips` 与奖励/预览共用，防两处漂移。
> - **无候选即不出卡**：`build_reward_pool()` 在没有任何有效灌注时过滤掉 symbol 卡。
> - **消耗品前置确定**：`_consumable_payload()` 展示前定物，腰带满时卡片直接写「腰带已满 → 折算金币 +N」，应用按 payload 入腰带/折金。
> - **回归**：M1 套件新增 8 条断言（候选真实增格 / payload 定符号 / 无二次随机 / 无有效灌注不出卡 / 消耗品定物与折金）。

## 6. 每阶段统一验收与提交纪律

### 6.1 每个任务的最小交付单元

一个可提交任务必须包含：

1. 代码或资源改动。
2. 对应 UI/tooltip/图标，或明确说明暂用回落。
3. 自动测试与必要的 F6 验证。
4. 文档状态回写。
5. 可独立回退的提交。

不允许先留下大量“功能已写但奖励不可达、图标以后再补、文档以后再改”的半成品。

### 6.2 自动验证

- 每个里程碑运行 `run_smoke.bat`，要求 8/8 全绿。
- 新机制增加定向回归，不能只依赖旧测试。
- 装备批次运行 `tests/p1b_baseline.tscn`。
- 涉及成长、奖励和存档时验证同种子可复现与存档迁移。
- 演出、UI 和成长选择不得消耗全局 RNG。

### 6.3 人工验证

每个里程碑至少走通：

```text
整备 → 战斗 → 成长/奖励 → 商店/替换 → BOSS → 结算 → 重开
```

按阶段补充 ACT1、完整三幕、老存档、新档和导出 Demo。

### 6.4 停止条件

出现以下情况时，不继续扩大下一批：

- 自动回归失败或新增定向测试缺失。
- 正常流程出现不可达奖励、死升级或假选项。
- 美术样板未获用户确认。
- ACT1 成长造成明显弹窗疲劳或节奏拖延。
- 真实构筑显示核心循环存在结构性问题。
- 新装备只是换名换色，无法提供可解释差异。
