## 第一部分：架构评审

### 1. 对 v2.0 的总体判断

v2.0 是一份**目标架构级别**的设计，方向正确且完整：8 模块职责清晰、数据与执行分离、品质不作为候选池入口、组合采样而非 Top3、强调可测试与调试输出。相比 v1.1 的"逐步改良"，v2.0 是彻底重写——这与用户"一次性做完、不要兼容"的决定一致。

**但我必须指出：v2.0 的 8 模块设计如果原样落地，会与项目现状产生三处结构性冲突，须在 Phase 0 解决：**

| # | 冲突 | 说明 |
|---|---|---|
| C1 | **模块粒度超出项目体量** | 8 个模块 + Snapshot + Evaluator + Composer + Resolver，对应当前实际只有 9 张 reward、7 种成长候选、约 2700 行奖励代码。空转抽象层过多，容易变成"为实现架构而架构" |
| C2 | **Reward Resolver 与现有结算重复** | v2.0 要求新建 `RewardResolver` 统一执行效果，但项目已有 `reward_system._apply_loot_option()` + `apply_reward()` 两套结算分支。不处理会形成两套并行结算路径 |
| C3 | **UI 数据契约变更面被低估** | `reward_screen` / `card_factory` / `battle_hud` 三处读 `view["quality_name"]`、"三项同层"文案、品质颜色。改为"每张卡自带品质"要同步改这三处 + 重抽/跳过 |

### 2. 已被源码核验支持的设计（无需再验证）

- ✅ **结算不读品质**：`settle_loot_offer()` 全函数无 quality 引用——这是 v2.0 §8"品质不作为候选池入口"能落地的关键前提。
- ✅ **品质决策点单一**：只在 `LootOffer.build()` 调 `roll_quality()` + `tier_items()`。
- ✅ **RNG 已隔离**：`LootPool._rng`（有 seed），重构后继续用这一条流，不碰 `randf()`。
- ✅ **目录扫描已正确**：`ResourceScan.scan_resources()` 用 `ResourceLoader.list_directory()`（导出安全），新增 RewardDefinition 资源直接复用。
- ✅ **单敌结构**：`RoomData` 无多目标字段——v2.0 §19 把多敌传播排除 MVP，正确。

### 4. 推荐的落地架构（对 v2.0 的收敛版）

> 🔒 **已按 v2.0 (1) 附录 B 的正式决议更新**（B.1 模块收敛 / B.2 Resolver 委托 / B.3 五张种子卡 / B.4 卡面品质展示）。
> 附录 B 决议优先于本文早前的建议。

按附录 B.1 决议，采用 **5 个核心运行时模块**（Evaluator 与 Composer 保持独立），加 1 个 Resource 数据定义 + 1 个 UI 适配：

```
scripts/reward/
├── reward_definition.gd     # RewardDefinition Resource（数据定义，非运行时模块）
├── reward_registry.gd       # 核心① Registry：扫描 .tres + 标签索引 + 校验（static）
├── run_state_analyzer.gd    # 核心② RunStateAnalyzer：capture(ctrl) → RunSnapshot（static）
├── reward_evaluator.gd      # 核心③ RewardEvaluator：base/context/synergy/novelty/risk 评分（static）
├── draft_composer.gd        # 核心④ DraftComposer：硬过滤 + 组合生成 + 多样性 + fallback + RNG
└── reward_resolver.gd       # 核心⑤ Resolver：委托现有 apply_loot_option，不重写结算

scripts/ui/
└── reward_presentation.gd   # DraftResult → UI view 数据契约（新，非核心运行时模块）
```

**与早前建议的差异**：早前我把 Eligibility/Evaluator/Composer 三合一成 `reward_draft_engine.gd`；附录 B.1 决议要求 Evaluator 与 Composer 独立，故改为 `reward_evaluator.gd`（纯评分，static）+ `draft_composer.gd`（过滤/组合/兜底/RNG）。**硬过滤放在 Composer**（v2.0 §7.2 属生成环节），评分放 Evaluator，职责更清晰。

**RewardResolver 的关键决策（附录 B.2 已锁定）**：**不重写结算**，而是包装现有 `reward_system._apply_loot_option()`。新卡通过 `effect_id` 映射到现有分支；确实需要新效果的（如免费重转 `_free_spin`、跨房盾 `run_shield_next`）在 Resolver 里加清晰的分发分支，仍走 controller 的既有状态字段。避免 C2 的双结算路径；且**新 Draft Engine 不得反向依赖旧抽选器**。

### 5. 数据结构定义（Phase 0 定稿用）

**RewardDefinition（extends Resource，`resources/rewards/defs/*.tres`）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | 稳定唯一 ID |
| `name` / `desc` | String | 展示文案 |
| `icon` / `art` | Texture2D | 表现资源（art 空则用 icon） |
| `rarity` | String | common/uncommon/rare/epic（战利品品质四档，与 RewardData 三档稀有度区分） |
| `tags` | Array[String] | 开放标签命名空间（survival.* / offense.* / build.* / control.* / economy.* / risk.* / element.* / weapon.* / symbol.* / discovery.*） |
| `base_weight` | float | 基础权重，默认 1.0 |
| `base_value` | float | 设计基准价值（用于评分，≠效果数值） |
| `effects` | Array[Dictionary] | `[{effect_id, params}]`，支持多效果，解决旧 `value:int` 表达不了复合效果的问题 |
| `stack_rule` | int enum | none/linear/diminishing/replace |
| `max_stack` | int | -1 表示无限 |
| `eligibility` / `context` / `synergy` | String | 规则键名，映射到引擎内的规则函数（数据驱动，不硬编码每张卡） |
| `unlock_rules` / `offer_frequency` / `risk_cost` | Dictionary | 可选 |

**RunSnapshot（纯值对象）**：只纳入项目真实存在、可可靠计算的字段——
`hp/max_hp/hp_ratio/shield`、`gold`、`room_index/act/kind`、`owned_rewards/tags`、`weapon paths & mastery`、`symbol paths & weights`、`perk_ids`、`shop_distance`（若无可靠数据则留空，不强造预测系统）。

**DraftResult**：`rewards:Array[RewardDefinition]` + `draft_id:String` + `debug_metadata:Dictionary`（评分/过滤原因/组合分）。

### 6. 抽选算法（落地的可执行版本）

```
1. snapshot = RunSnapshot.capture(ctrl)          # 只读
2. pool = RewardRegistry.all()                   # ResourceScan 扫描
3. eligible = _eligible(pool, snapshot, ctrl)    # 硬过滤：上限/无目标/已拥有/条件不成立/重复无收益
4. scored = _score(eligible, snapshot)           # base_value + context + synergy + novelty + risk + progression
                                                 # 各项有封顶，线性/分段，禁止 ML
5. compose: 采样 N 组候选 draft（每组 3 张）
   DraftScore = ΣOfferValue - SimilarityPenalty + PairSynergyBonus + ChoiceTensionBonus + Randomness
6. 从高分 draft 中带权抽一组（非唯一 Top1，保留探索）
7. 校验：≥2 功能差异、无硬冲突；不足则放宽软约束重采
8. 仍不足 → 用标记为 fallback 且当前有效的 RewardDefinition 补齐；绝不空屏/假卡
9. 冻结参数 → DraftResult（展示与结算共用同一份实例）
```

治疗价值用有效恢复量：`eff_heal = min(heal, max_hp - hp)`，评分考虑 `eff_heal` 但不机械惩罚；低血保证"至少一个有效生存解法"（可治疗/护盾/免死），非"必出治疗"。

### 7. 迁移边界（明确不做什么）

**保留不动**：`settle_loot_offer` 调用链、`room_flow` 战后流程、BOSS 奖励、存档、战斗系统、商店/铁砧经济、现有 9 张 RewardData（作为旧内容盘点来源，不直接删）。

**替换**：`GrowthLootOffer._rebuild` 候选生成、`LootOffer.build` 品质选层、`card_factory` 的卡牌 view 构造、`reward_screen` 的展示文案/重抽/跳过。

**桥接**：新 `RewardResolver` 委托现有 `apply_loot_option`；新 UI Presentation Model 产出与旧 view 兼容的字段（`title/desc/icon/quality/quality_name/...`），让 `reward_screen` 改动最小化。

### 8. 风险清单

| 风险 | 对策 |
|---|---|
| 评分模型过度复杂 | 线性/分段 + 各项封顶；Phase 1 只做 base/context/synergy 三项 |
| 过度迎合玩家 | 带权采样 Top 组而非 Top1，保留 Randomness 与 Novelty |
| 双结算路径 | Resolver 委托现有 `apply_loot_option`，禁止另起炉灶 |
| UI 品质文案不同步 | Presentation Model 统一产出 view；"三项同层"改为卡自带品质，三处同步 |
| class_name 缓存陈旧 | 生成后删 `.godot/global_script_class_cache.cfg` + headless 重建 |
| 卡池不足兜底退化 | Fallback 必须注册在 Registry 且通过 Eligibility，禁止假卡 |
| 测试覆盖不足 | 每个 Phase 配 .tscn 测试；Phase 1 先跑通"3 张有效/过滤正确/可复现" |
