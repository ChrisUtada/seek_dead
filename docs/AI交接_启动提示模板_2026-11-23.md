# AI 交接 · 启动提示模板

> 日期：2026-11-23
> 用途：每轮审查结束后，把「本轮要改什么」填进本模板，整段复制给执行 AI。
> 约定来源：设计基线 §6 执行纪律第 9 条。
> 维护规则：固定段落不要改（仓库、禁止项、验证口径、回报格式）；只替换 `{{ }}` 槽位。

## 填槽时的固定口径

| 槽位 | 口径 |
|---|---|
| 仓库路径 | 绝对路径，不用相对路径 |
| Godot 引擎 | 用 `..._console.exe`，否则拿不到 stdout |
| HEAD | `git rev-parse --short HEAD` 的实值；不要写"最新" |
| 未提交改动 | 逐项列出文件名，明确"必须保留" |
| 级别 | 沿用文档口径：P0 阻断 / P1 必修 / P2 顺手 |
| 验证 | 只写**能判定通过**的命令；每条都要有 RESULT 行 |
| 通过标准 | 不写"全绿"；写具体 `RESULT` 前缀与 `fails=0` |

## 禁止的写法

- 写"跑一下相关测试"——执行方会自选，覆盖不可预期。
- 写"全量回归通过"——除非确实逐脚本跑过并贴了结果。
- 用退出码判绿——Godot 在 PowerShell 下 stderr 会污染 `$LASTEXITCODE`。
- 把 checks 总数当固定基线——部分 bot 的断言数随房间/机制走，每次不同。
- 把"某个 bot 失败"直接归因为产品回归——先分清是生产行为正确打断了旧 bot，还是真的回归。
- 在 PowerShell 里用 cmd 变量传参（`cmd /c "run_smoke.bat %g%"`）——`%g%` 不会展开，会静默变成字面量；M-05 首跑因此报 "Godot exe not found"。统一用 `$g` 或直接写字面路径。

## 完整版结构（2026-11-24 起固定）

从 M-05 那一轮开始，提示统一按**分组执行单**写，不再只列"代码要改哪几处"。固定五组：

| 组 | 内容 | 为什么必须写进同一段 |
|---|---|---|
| A | 验收补齐：能失败的断言、**改前红证据** | 否则执行方只交"全绿"，没人证明断言有判别力 |
| B | 设计/供给决策：二选一 + 各自做法 | 删除或放宽机制时，代价必须当场定，不能留到下一轮 |
| C | 回归门禁：把新套件登记进 run_smoke、修既有红测试 | 不进闸门的测试等于只跑过一次 |
| D | 文档记账：基线状态、§3.3 证据、独立实施记录、外部生成稿标注 | 否则口头结论会丢，下一个人只能靠对话考古 |
| E | 提交拆分：commit 分组 + message 要写什么 | 混装提交会让后续归因失效 |

配套三条硬性要求，缺一不算完成：

1. A 组必须包含"先证明改前红"的操作步骤与期望失败项，并回报日志。
2. B 组必须给出选项与代价，由执行方在回报里写明选了哪个、为什么。
3. 验证段末尾固定加一句「APPDATA 隔离、串行、只看 RESULT 行、不用退出码判绿」。

## 插件/工具类任务的写法

工具轮不套 A–E（那是仓库交付件），但仍要写清四件事：装到哪（绝对路径，且不得落在游戏仓库内）、如何生效（重启/热加载）、如何验证（可观测的标记文件或命令）、如何回滚（备份路径 + 撤销步骤）。
