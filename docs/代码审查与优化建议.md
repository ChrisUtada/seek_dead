# 代码审查与优化建议（duel 战斗层）

> 评审对象：`scripts/battle/duel_controller.gd`、`scripts/ui/battle_hud.gd`、相关 `.tscn`。
> 评审目标：最佳实践、低耦合高内聚、尽量使用编辑器可视化操作。
> 本文档为**诊断 + 分阶段优化路线**，不改动现有行为；每阶段独立、可单独 F6 验证、可单独回滚。

---

## 一、现状度量（实测数据，非印象）

| 指标 | duel_controller.gd | battle_hud.gd | 说明 |
|---|---|---|---|
| 行数 | 2097 | 1609 | 两个千行级文件 |
| 顶层函数 | ~100 | ~100 | 单文件职责过多 |
| 顶层变量/常量 | ~90 | ~90 | 状态高度集中 |
| `add_child` 调用 | 3 | **173** | HUD 全靠代码拼 |
| `.new()` 实例化 | 2 | **83** | 运行期 new 节点 |
| controller → HUD 调用 | **163 次 / ~35 个成员** | — | 含戳 `hud.cells`、`hud.reward_screen`、`hud._build_ui` 等**内部件** |
| HUD → controller 调用 | — | **141 次 / ~40 个成员** | 连 `controller.charm_power_bonus`、`controller.meta`、`controller._shop_name` 等**私有**都读/调 |
| signal 定义 | 1（`spin_finished`） | 0 | 解耦机制几乎为零 |
| `battle_hud.tscn` | — | **10 行空壳**（仅 `Control` 根 + 脚本） | 布局零可视化 |
| `duel.tscn` | 12 行空壳 | — | 同上 |

**一句话结论**：两个文件都在朝「全代码、单文件、双向直连」的方向长，与项目自己定的「表现/逻辑分离」原则已经出现明显落差。

## 二、值得保留的好实践（不要动）

评审不是全盘否定。以下做得对，后续重构要**守住**：

1. **数据层 = Resource(.tres) + `@export` 直接引用**：符号/武器/护符/房间全是 `.tres`，加内容不改代码——这是项目最重要的架构铁律，非常 Godot-native。
2. **平衡常量集中且有注释**：`ANTE_*`、`CHAIN_*`、`WEIGHTS`、`MISS_FLOOR/CEIL` 等都带设计意图注释，调参意图清晰。
3. **可复用 UI 组件已起步**：`ui_button.tscn`、`ui_panel.tscn`、`symbol_cell.tscn` 是真正的可视化组件（57–79 行有布局），这个方向要继续扩。
4. **无全局注册表 / 枚举字典查表**：资源靠扫描 + 直接引用，没有反模式的 CATALOG。

## 三、三大核心问题

### 问题 1：duel_controller 是「上帝对象」（低内聚）

2097 行塞了 6 个本该独立的职责域：

| 职责域 | 代表函数 | 行号段 |
|---|---|---|
| 转轮引擎 | `_build_pool` / `_build_strips` / `_begin_spin` / `_on_spin_tick` / `_write_reel_cell` / `_finish_spin` | 315–1500 |
| 结算引擎 | `_evaluate` / `_contribute` / `_push_dmg_line` / `_agg_*` / `_buff_*` / `_status_*` | 1742–2089 |
| 经济 | `_award_gold` / `_shop_*` / `_on_shop_*` / `_anvil_*` / `_gold_upgrade_*` / `_save_meta` | 786–1075 |
| 房间/run 流程 | `_build_run` / `_sort_rooms` / `_start_room` / `_enemy_turn` / `_full_reset` | 1077–1540 |
| 装备/loadout | `_confirm_loadout` / `_apply_charms` / `_cat_*` / `_grow_slot` / consumable panel | 401–535 |
| 奖励 | `_roll_rewards` / `_apply_reward` / `_on_reward_*` / `_roll_meta_*` | 544–785 |

**为什么是问题**：改任何一个域都要在 2000 行里翻，函数间通过 ~90 个共享顶层变量隐式通信，改 A 域容易碰坏 B 域（最近几次 F6 报错正是这种「隔行误伤」）。

**改成什么样（高内聚）**：按职责拆成**专注的组件**。推荐先抽**纯逻辑**（不依赖节点、不碰 UI）进库脚本，controller 只留编排：

```
scripts/battle/
  reel_engine.gd      # pool_items/strips/spin 状态机，输出 reel_strips + 信号
  combat_resolver.gd  # _evaluate/_contribute/_agg_*/_buff_*/_status_* 纯结算
  economy.gd          # gold/shop/anvil/meta/rewards 数值逻辑
  duel_controller.gd  # 瘦身成编排者：持有上述组件、转发信号、管流程
```

> 风险最低的第一步：把 `_agg_*`、`_buff_*`、`_status_*`、`_status_base`、`_status_element` 这类**纯函数**（只进参数、出返回值、不碰 `hud`）先抽到 `combat_resolver.gd` 或 `battle_math.gd`，controller 改为调用。零行为变化、零节点依赖，F6 一次即可验证。

### 问题 2：controller ↔ HUD 双向紧耦合（低内聚 + 高耦合）

这是最伤的一点。双向各 ~150 次直连，且大量穿透 `_` 私有约定：

- **controller → HUD**：`hud._log`（79 次）、`hud._refresh_meta`（19 次），还直接戳 `hud.cells`、`hud.reward_screen`、`hud._build_ui`、`hud.legend_container`——逻辑层在操控 UI 的内部零件。
- **HUD → controller**：直接读 `controller.grid`、`controller.meta`、`controller.enemy_*`、`controller.charm_*`，还直接调 `controller._cat_max`、`controller._shop_name`——表现层在长驱直入逻辑层的私有状态。

**为什么是问题**：`hud._log` 改个签名要在 79 处跟进；controller 想改个内部字段名，HUD 141 处跟着炸。两边都无法独立测试、独立复用。这正是「表现/逻辑分离」只停在了文件层面、没落到调用层面。

**改成什么样（单向数据流 + 信号解耦）**——这是本次评审**最高优先级**：

```
                 ┌────────────────────┐
   用户输入意图   │                    │  只读状态快照
  ┌────────────► │  DuelController    │ ──────────────┐
  │  (信号)       │  (逻辑/状态唯一权威) │               │
  │              │                    │               ▼
  │              └────────────────────┘        ┌─────────────┐
  │                                            │  BattleHud  │
  └────────────────────────────────────────────│ (纯渲染)     │
             spin_requested / buy_requested     └─────────────┘
```

1. **HUD → controller 只发「意图信号」**：HUD 不再调 `controller._shop_name()`、`controller._on_shop_sell_pressed()`，而是 `emit_signal("buy_requested", offer)`、`emit_signal("spin_requested")`，由 controller 连接处理。HUD 也不需要知道 controller 的字段名。
2. **controller → HUD 只推「只读快照 + 语义方法」**：controller 维护一个 `BattleState`（Dictionary 或 Resource），每阶段填充后让 HUD 渲染；controller 不再戳 `hud.cells`/`hud.reward_screen`，而是调 HUD 提供的少量**公开语义接口**（`hud.show_damage(...)`、`hud.set_reels(...)`），或干脆发信号让 HUD 自己刷新。
3. 落地后：300+ 次跨层直连 → 收敛为「一打信号 + 一个状态结构」。`_` 私有约定重新成立。

> 阶段化：先定义 `BattleState` 快照替代 HUD 的 141 次**读**（只读、相对安全）；再把 HUD 的**写/调用**改成信号。分两步，每步独立 F6。

### 问题 3：全代码 UI，零编辑器可视化

`battle_hud.tscn` 是空壳，整屏布局（玩家/敌人面板、转轮格、loadout/shop/reward/anvil/meta 五套覆盖层、日志、飘字）全用 173 次 `add_child` + 83 次 `.new()` 在 `_build_ui()` / `_build_xxx_screen()` 里 new 出来。

**为什么是问题**：
- 调布局要读代码脑补结构，无法在设计器里拖拽预览；
- 对齐/锚点/间距写成魔法数字埋在代码里，改一个边距要找半天；
- 这正是你说的「没尽量用编辑器可视化」——Godot 的核心生产力被放弃了。

**改成什么样（编辑器可视化）**——把「静态结构」搬进 `.tscn`，代码只留「动态数据绑定」：

| 现在（代码） | 改成（编辑器） |
|---|---|
| `_build_ui()` new 出玩家/敌人面板、Label | 在 `battle_hud.tscn` 里**可视化拖好**面板与 Label，脚本用 `@onready var hp_label: Label = %PlayerHpLabel` 引用（**唯一节点名 `%`**） |
| `_build_loadout_screen()` 等 5 套覆盖层全代码 | 每套拆成独立 `.tscn`（`loadout_screen.tscn` …），编辑器搭静态骨架；代码只做「填数据、显隐」 |
| Label 字号/颜色/间距写死在 `_label()` | 收敛到 `battle_theme.tres`（已在用）+ 编辑器里设 `theme_type_variation` |
| 平衡常量写死 `const` | 需要策划调的（`ANTE_*`、权重、`CHAIN_*`）改 `@export`，**直接在 Inspector 里拖数值**——这也是「编辑器可视化」 |

**仍然适合留代码的部分**（不要矫枉过正）：数据驱动的**动态列表**（商店货架、loadout 卡片、日志行、飘字池）本来数量不定，用代码实例化复用组件（`symbol_cell`/`ui_button`）是正确且必要的——把组件本身做可视化即可。

## 四、最佳实践细节清单（顺手收敛）

1. **类型标注**：大量 `var x = []` / `var x = {}` 无类型。逐步补 `Array[Dictionary]`、`Dictionary`、显式 `float/int`，让 Godot 静态检查帮你挡错（最近的报错很多能提前暴露）。
2. **私有约定落到实处**：`_xxx` 只在文件内部用；跨文件一律走公开接口/信号（见问题 2）。
3. **魔法数字 → 资源/导出**：UI 尺寸、颜色进 `battle_theme.tres`；平衡数值进 `@export` 或独立的 `BalanceConfig.tres`。
4. **`_input` 事件**：2097 行里 `_input` 与点击列逻辑耦合在 controller，可把「点击第几列」封装成 HUD 的 `reel_clicked(col)` 信号，controller 订阅。
5. **命名一致性**：`_build_ui`/`_build_xxx_screen` 在 controller 里被直接调用（`hud._build_ui`）——建 UI 应该是 HUD 自己的事（`_ready` 里自建），controller 不该代劳。

## 五、分阶段路线图（每步独立、可单独 F6、可单独回滚）

> 原则：**先零风险纯函数抽取，再解耦，最后可视化**。本机无 Godot 二进制，所有 F6 由你做，故每阶段都要能单独验证。

| 阶段 | 内容 | 风险 | F6 验证点 | 状态 |
|---|---|---|---|---|
| **P0** | 抽纯函数（`_agg_*`/`_buff_*`/`_status_*`/`_status_base`/`_status_element`）到 `battle_math.gd`，controller 改调用 | ★ 极低（纯函数、无节点依赖） | 数值与重构前完全一致 | 🟢 已落地（`90822e3`，F6 通过，用户确认数值一致） |
| **P1** | 定义 `BattleState` 只读快照，替换 HUD→controller 的 141 次**读** | ★★ 中（只读快照） | 各面板/标签/图例显示正确 | 🟢 已落地（`5298c5b`，117 处数据字段读改走 `controller.state`，逻辑/动作方法保留 controller 调用）；⚠ F6 连续发现 2 处快照误用：① `consumable_panel`（UI 节点）误入快照 → `_build_ui` 报 "Nonexistent function ... in base Nil"，fixup `3011c66` 还原为 `controller.consumable_panel`、快照只装数据不装节点；② P1 批量替换误把「动作/写回」也路由到 `controller.state`（只读快照 getter 每次返回全新 BattleState，对其赋值/重赋值不反映到 controller 真实字段）→ 胜利后奖励三选一卡片不生成（`reward_choices` 重赋值落入 throwaway 快照）、`in_loadout` 守卫失效、grid 写快照违背只读语义，fixup `0eabbe0` 将 _show_reward_screen / _show|_hide_loadout_screen / _build_ui 的写回全部收敛到 `controller.`、state 仅作只读 |
| **P2** | HUD 的**调用**改信号（`spin_requested`/`buy_requested`/`reward_chosen`…）；controller 不再戳 `hud.cells`/`hud._build_ui` | ★★ 中 | 点击交互、商店买卖、奖励三选一 | 🟢 已落地（`8c922bd`；HUD 顶部声明 7 个意图信号 + `build_all()`/`set_reel_enabled()`/`hide_*_screen()` 公开语义接口；controller 在 `_ready` 订阅信号、不再直戳 `hud._build_*`/`hud.cells`/`hud.*.visible`；范围外按钮 purify/reload/loadout/meta/anvil/gold_upgrade/overlay 的 `controller._on_*` 直连保留，属后续解耦） |
| **P3** | 编辑器重建 `battle_hud.tscn` + 5 套覆盖层 `.tscn`，脚本改 `%` 引用；平衡常量转 `@export` | ★★★ 较高（UI 重建） | P3a：常量 @export（Inspector 调参）；P3b：布局、对齐、五套界面显隐 | 🟢 P3a 已落地(cfce4e5)；P3b ⚪ 未开工 |

建议**一次只做一阶段**，推一个 commit、F6 通过再进下一阶段。P0 可以马上做（最安全、收益立竿见影——duel_controller 立刻瘦身且结算逻辑可独立单测）。

## 六、不做的事（避免过度工程）

- 不引入第三方事件总线/依赖注入框架——Godot 原生 signal + 状态快照足够。
- 不把动态列表（商店/卡片/日志/飘字）硬塞进 `.tscn`——数据驱动的留代码实例化复用组件。
- 不动数据层（Resource/.tres）与平衡常量注释——那是项目最对的部分。
