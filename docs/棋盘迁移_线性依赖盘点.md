## 0. 结论摘要

线性流程的耦合不是「房间数组」一处，而是 **5 条隐含假设**：

| # | 假设 | 影响面 | 迁移时必须替换为 |
|---|---|---|---|
| A | 当前房间 = `ROOMS[room_index]` | 25 个脚本（含 13 个 gimmick） | `ctrl.current_room` 单一来源 |
| B | 下一房间 = `room_index + 1` | `room_flow`、HUD 下一房预告 | 棋盘 `next_node()` |
| C | 最终战 = `ROOMS.size() - 1` | `duel_controller`、`room_flow`、`anvil_system`、测试 | 显式 `run_final` / 最终 BOSS 节点 |
| D | 难度 = 本幕内数组位置 `ria` | `run_setup.ante_scale` | 本幕**已进入战斗房计数**（与棋盘节点解耦） |
| E | 当前幕 = `ROOMS[room_index].act` | `reward_system`、HUD、`anvil_system` | `ctrl.current_act` |

其中 A 面最广（72 处引用、25 个文件），但结构最简单：13 个 gimmick 是同一行复制粘贴，可一次性替换为访问器。真正的设计风险在 **C（终局语义）** 和 **D（难度曲线）**——这两处不先定，棋盘的「12 节点、实际经过 7–8 个」会直接改变 ACT1 的数值曲线。

统计：`ROOMS` / `room_index` 在 `scripts/` 共 **72 处 / 25 文件**，`tests/` 共 **87 处 / 12 文件**。

## 2. 四个状态源的现状与目标

文档 §10.2 要求四个状态各有明确来源。现状与目标如下：

| 状态 | 现状来源 | 问题 | 目标来源 |
|---|---|---|---|
| 当前房间 | `ROOMS[room_index]` | 棋盘节点不是数组下标 | `ctrl.current_room: RoomData`（棋盘由节点携带；线性由数组填入） |
| 当前幕 | `ROOMS[room_index].act` | 商店/休整节点没有 RoomData | `ctrl.current_act: int`（棋盘节点自带 act；线性取 RoomData.act） |
| 已访问节点 | 无（隐含为 index） | 棋盘需要消耗、分支、回头查看 | `BoardSystem` 运行时状态（当前节点、已消耗、已选分支、骰子结果） |
| 最终战 | `ROOMS.size() - 1` | 棋盘总节点 ≠ 战斗房数，位置判定失效 | `ctrl.run_final: bool`（由最终 BOSS 节点置位） |
| 下一节点 | `ROOMS[room_index + 1]` | 棋盘有分支和 1D3 | `BoardSystem.next_candidates()` / `next_node()` |

实现建议：四个字段先加在 `DuelController`，线性模式在 `_start_room(idx)` 里同步写入；棋盘模式由 `BoardSystem` 写入。所有消费方只读字段，不读数组。

## 3. 迁移接口契约（草案）

### 3.1 DuelController

```gdscript
var current_room: RoomData = null      # 当前战斗房；商店/休整节点为 null
var current_act: int = 1
var current_room_ria: int = 0          # 本幕已进入的第几个战斗房（0 起）
var run_final: bool = false            # 本节点是否为整局终点
var node_mode: bool = false            # false = 线性（默认）；true = 棋盘

func start_room_data(r: RoomData, ria: int, is_final: bool) -> void:
    # 现 _start_room 的实体逻辑迁入此处；只依赖传入参数，不再读 ROOMS[idx]
func _start_room(idx: int) -> void:
    # 线性适配器：start_room_data(ROOMS[idx], ria_of(idx), _is_run_final(idx))
```

约束：

- `_is_boss_room(idx)` 保留，但实现改为 `current_room != null and current_room.kind == "boss"`（签名可保留以兼容测试）。
- `_is_run_final(idx)` 保留为线性兼容，但内部改为 `run_final`（线性模式由适配器写入）。
- `_start_room(idx)` 与 `start_room_data()` 必须走同一套实体初始化，禁止复制两份。

### 3.2 BoardSystem（M2 新增）

```gdscript
func current_node() -> BoardNodeData
func roll_dice() -> int                    # 1D3，全局 RNG，种子可复现
func legal_targets() -> Array[BoardNodeData]
func advance_to(node_id: String) -> void   # 只允许前向；一次性结算
func is_final_node() -> bool
func consume(node_id: String) -> void
```

边界（文档 §10.2 原样落地）：

- 棋盘只决定「进入哪个 RoomData / 节点」，不写伤害。
- `advance_to` 对落点效果做一次性闸门（`_resolving` 标志），重复点击不重复结算。
- 动画只用本地 RNG 或纯视觉插值，不碰全局 RNG。

### 3.3 RoomFlow / HUD

| 位置 | 线性 | 棋盘 |
|---|---|---|
| `room_flow.on_next_room_pressed` | `_start_room(room_index + 1)` | `board.advance()` → 按节点类型进入战斗/商店/休整/拾取 |
| `battle_hud._refresh_next_room_bar` | 现有实现 | `node_mode` 时隐藏（棋盘即预告） |
| 房间行 | `房 x/y` | `节点 x/12` |
| BOSS 机制摘要 | `ROOMS[room_index]` | `current_room` |

### 3.4 gimmick 访问器

13 个 gimmick 的同一行替换：

```gdscript
# 旧
var p: Dictionary = ctrl.ROOMS[ctrl.room_index].gimmick_params if (...) else {}
# 新
var p: Dictionary = ctrl.current_room.gimmick_params if ctrl.current_room != null else {}
```

行为完全等价；建议单独一个提交，跑 14 套回归确认零变化。

## 4. 难度曲线（最高风险项）

`run_setup.ante_scale(r, idx)` 现在这样算幕内位置：

```gdscript
var ria = 0
for i in range(idx + 1):
    if rooms[i].act == a: ria += 1
ria -= 1
hp_scale = 1.75^(act-1) × 1.15^ria
atk_scale = 1.30^(act-1) × 1.06^ria
```

线性 ACT1：8 房 → `ria` 0..7，第 8 房（BOSS）hp×2.66 / atk×1.50。

棋盘 ACT1：12 节点、实际经过 7–8 个，其中战斗节点 4 普通 + 2 精英 + 1 BOSS = **7 场**。若 `ria` 改按「第几个节点」算，难度曲线会整体前移；若按「第几个战斗房」算，仍是 0..6，BOSS 略低于线性（2.31 vs 2.66）。

**建议**：`ria` 只对战斗节点递增（商店/休整/拾取不计），并把 ACT1 的 7 场战斗视作与线性 8 房等价的爬升——即 BOSS 保持 `ria = 7` 的方法是把「进入 BOSS 前已打 6 场」映射到 7，或直接把 BOSS 的 `ria` 固定为本幕战斗房总数。这一点必须在 M2 灰盒前用 `p1b` 对照拍板，不能默认沿用。

**验收**：棋盘 ACT1 的普通房承伤 / BOSS 回合数，与线性基线（`p1b_baseline`）偏离不超过 ±30%，否则先调映射再继续。

## 5. 奖励与战后成长的边界（M1 相关）

> 2026-11-05 更新：M1 已落地（`docs/M1_战后成长合并_2026-11-05.md`）。当前胜利链已改为
> `turn_flow 胜利 → hud._show_reward_screen → room_flow.begin_post_battle（先结算历练/熟练）
> → 三槽屏 → 选一项 → finish_post_battle → 间歇`；`_offer_next_growth_pick` 已移除，
> BOSS 仍走专属战利品。下表的「现状」保留为迁移前基线，M2 只需把 `_current_kind()` /
> `ROOMS[room_index]` 替换为 `current_room`，不再处理独立成长屏。

现状胜利链：

```text
turn_flow 胜利 → hud._show_reward_screen(is_boss)
→ reward_screen.show_screen → reward_system.open_reward_screen
→ 玩家选卡 → duel_controller._on_reward_chosen
→ room_flow.finish_room(apply → 铁砧/金币/掉落/历练/熟练 → _offer_next_growth_pick)
→ 成长结算（技艺 + 铭印）→ enter_interroom
```

M1 要把「奖励屏」与「成长结算」合并为一次三槽选择，涉及：

| 文件 | 现状 | M1 处置 |
|---|---|---|
| `turn_flow.gd` | 5 处显示奖励屏 | 改为显示统一「战后成长」屏 |
| `reward_screen.gd` | 只渲染奖励卡 | 被三槽屏替代或扩展 |
| `room_flow._offer_next_growth_pick` | 奖励屏关闭后再弹成长 | 合并进三槽生成，成长位走队列 |
| `reward_system.roll_rewards / roll_elite_rewards` | 普通/精英两套池 | 作为补给位/构筑位候选来源 |

| `_is_run_final` | BOSS 后跳过普通奖励 | 保持不变（BOSS 专属战利品） |

M1 不依赖棋盘，可以先在线性房间上独立验收；本文的接口契约不影响 M1，但 M1 的三槽屏最好以「节点类型参数」而非 `room_index` 取数，避免 M2 再改一次。

## 6. 测试与回归策略

### 6.1 保留双模式

- 默认 `node_mode = false`，现有 14 套回归全部走线性，**不因棋盘改造而失效**。
- 新增 `node_mode = true` 的棋盘测试，单独跑。
- `m4_demo_test` 的 `ROOMS.size()` 断言只对线性模式成立；棋盘模式新增「节点数 = 12」断言。

### 6.2 新增棋盘测试（M2 出口）

对应文档 §12.1：

1. 同种子生成相同拓扑、房间、物品、骰子序列。
2. 所有 BOSS 可达、无孤立节点、无死路。
3. 骰子 1/2/3；分支落点；超过 BOSS 停在 BOSS；节点一次性消耗。
4. 同一落点重复点击不重复结算。
5. 商店/休整/武器/护符/BOSS 的进入与返回状态。
6. 动画不消耗全局 RNG（对比前后 `randi()` 序列）。

### 6.3 迁移期提交纪律

每步独立提交、独立跑 14 套：

| 步骤 | 内容 | 回归 |
|---|---|---|
| 1 | 状态源收敛（加字段 + 适配器，无行为变化） | 14/14 必须全绿 |
| 2 | gimmick / reward / anvil / HUD 改读 `current_room` | 14/14 必须全绿 |
| 3 | `ante_scale` 改显式 `ria` + p1b 对照 | 14/14 + p1b 偏差 ≤30% |
| 4 | M1 战后成长合并（仍线性） | 14/14 + 新三槽测试 |
| 5 | M2 棋盘灰盒 | 14/14 + 棋盘测试 |

## 7. 待拍板问题（进入 M1 前需要确认）

1. **难度映射**：棋盘 7 场战斗如何对应线性 8 房的 `ria`？建议 BOSS 固定为满爬升，普通/精英按战斗序号。
