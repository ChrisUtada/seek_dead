## 0. 契约总览

| 项目 | 最终决议 |
|---|---|
| Effect Mapping | 5 个明确 `effect_id`，RewardResolver 统一分发；**只分发，不复制结算代码** |
| 幸运余波 | **每次战后三选一界面 1 次免费重抽**（不累积、不扣费、与付费重抽共用刷新入口） |

| Analytics | 复用现有 `run_telemetry.gd`，扩展事件/签名，不另建 Singleton |

## 1. Effect Mapping（5 个 effect_id）

### 1.1 正式映射

| 种子卡 | `effect_id` | 处理方式 | 类型 | 结算落点（源码核验） |
|---|---|---|---|---|
| 战场整备 `seed_battle_ready` | `heal` | 调用现有治疗结算 | 复用 | `reward_system._apply_loot_option` 的 heal 分支（`:552-560`） |
| 守护余烬 `seed_guardian_ember` | `shield_next_battle` | 写入下一战护盾 | 复用 | `reward_system.run_shield_next`（`:547`）；`duel_controller:1135` 开局消费 |
| 锋锐打磨 `seed_edge_polish` | `run_power_bonus` | 增加本局基础伤害 | 复用 | `reward_system.run_power_bonus`（`:574`）；`combat_system:844` 聚合 |
| 火焰共鸣 `seed_flame_resonance` | `flame_affinity` | 写入火焰构筑状态 | 新效果 | BuildState 标签 +1（见 §3） |
| 幸运余波 `seed_lucky_afterglow` | `free_reroll` | 增加免费重抽次数 | 新效果 | Draft 重抽状态（见 §2） |

> 🔴 **修正点 A**：后两项是新系统能力，**不得伪装成旧 `RewardData` 的结算类型**（旧 id 只有 heal/maxhp/symbol/shield/power/gold/consumable/weapon/maxhp_heal/elite_*）。它们必须通过新 Resolver 的独立分支接入。

### 1.2 Resolver 分发规范（强制）

```gdscript
# scripts/reward/reward_resolver.gd
func resolve_reward(reward: RewardDefinition) -> RewardApplyResult:
    match reward.effect_id:
        "heal":               return _apply_existing_heal(reward.effect_params)
        "shield_next_battle": return _apply_existing_shield(reward.effect_params)
        "run_power_bonus":    return _apply_existing_power(reward.effect_params)
        "flame_affinity":     return _apply_flame_affinity(reward.effect_params)
        "free_reroll":        return _apply_free_reroll(reward.effect_params)
        _:                    return RewardApplyResult.failure("unknown_effect_id")
```

**硬约束**：
- Resolver **只分发，不复制原有奖励效果代码**。旧结算接口不适合直连时做 Adapter，禁止在新 Resolver 里再写一套回血/护盾/伤害的状态修改逻辑。
- 每个效果执行必须返回 `RewardApplyResult`（成功/失败/effect_id/实际摘要/失败原因），**禁止出现"卡消失但效果没执行"**。
- Resolver 不得依赖旧抽选器（`LootOffer` / `GrowthLootOffer`），只可依赖旧**结算**接口（B.2 边界）。

## 2. 幸运余波：免费重抽规则（术语已修正）

### 2.1 🔴 修正点 B：这是"战后三选一重抽"，不是"战斗内转轮重转"

项目里有两种重转，契约锁定为**前者**：

| 概念 | 源码位置 | 是否本卡所指 |
|---|---|---|
| 战后三选一重抽（换 3 张奖励卡，付费 5+5×次数） | `reward_system.reroll_loot_offer()`（`:342`） | ✅ **是** |
| 战斗内转轮重转（重转老虎机转轮） | `duel_controller._free_spin()`（`:1625`）/ `turn_flow.free_spin()`（`:156`） | ❌ 否 |

理由：v2.0 B.3 定义幸运余波为"操控 / 免费重转"，用户建议明确写"重转后刷新 Draft""与付费重转共用同一套 Draft 刷新入口""免费次数>0不扣费"——全部指向**战后奖励卡的免费重抽**，不是战斗内转轮。契约按此锁死，避免 Agent 接错到 `_free_spin()`。

> 备注：用户建议中"每场战斗最多使用 1 次"的措辞，在战后奖励语境下应理解为"每次战后三选一界面 1 次"。因战后三选一发生在房间结算后、下一房开始前，这里统一为**每次奖励界面重置**（见 2.2）。

### 2.2 正式规则

| 项 | 决议 |
|---|---|
| 次数 | 每次战后三选一界面 **1 次**免费重抽 |
| 重置时机 | **每次生成新 Draft（进入战后奖励界面）** |
| 与付费重抽 | 完全独立；免费不消耗金币、不增加付费重抽次数、不影响付费价格递增 |
| 可否累积 | 不可累积 |
| 未使用 | 离开该奖励界面即失效 |
| 刷新入口 | 与付费重抽**共用同一个重抽函数**，内部先判免费 |
| 品质/稀有度 | 重抽后刷新规则由新 Draft 系统统一决定，不锁定旧选项 |

### 2.3 状态结构（落点）

```gdscript
# 战后奖励阶段状态（归属 RewardSystem / DraftComposer，非 HUD）
var draft_id: String = ""
var free_rerolls_remaining: int = 0     # 幸运余波提供，每次新 Draft 重置
var paid_rerolls_used: int = 0          # 付费重抽计数，用于价格递增
var paid_reroll_cost: int = 5           # 下次付费价格
```

> 🔴 **修正点 C**：不要用一个 `free_reroll_used` 布尔散落在 HUD 或 BattleController。统一在奖励阶段状态里维护。

### 2.4 重抽流程（免费优先）

```
请求重抽
    ↓
free_rerolls_remaining > 0 ?
    ├─ Yes → 次数 -1 → 重新生成 Draft（不扣费，不动 paid_rerolls_used）
    └─ No  → 检查金币 → 扣费 → paid_rerolls_used +1 → 价格递增 → 重新生成 Draft
```

## 3. 火焰共鸣：Build State 标签推导

### 3.1 核心原则

火焰构筑**不由单张卡触发**，由玩家当前实际拥有的武器、符号、技艺、构筑奖励共同计算。Evaluator 不直接扫描各系统，只读 `BuildState`。

### 3.2 标签来源

| 来源 | 是否参与 | 计算依据 |
|---|---|---|
| 武器 | 是 | 装备/持有武器的火焰属性与火焰机制（`WeaponData.element`） |
| 符号 | 是 | 转轮中火焰符号数量/权重（`SymbolData.element`） |
| 技艺 | 是 | 已拥有技艺是否带火标签/火焰协同（候选：现有 8 项技艺暂无纯火标签，需确认是否新增） |
| 构筑奖励 | 是 | 已获得的火焰构筑强化（如 `flame_affinity` 自身） |
| 消耗品 | 默认不参与 | 一次性，不构成永久 Build |
| 临时战斗 Buff | 默认不参与 | 避免流派判定跳变 |

### 3.3 统一标签命名（强制）

```
element.fire / element.ice / element.lightning
build.fire   / build.ice   / build.lightning
synergy.fire_weapon / synergy.fire_symbol / synergy.fire_skill
```

禁止 `fire` / `burn` / `flame` / `elemental` 混用无统一语义。一张卡可持多标签，例如火焰武器 = `[weapon, element.fire, build.fire]`。

### 3.4 BuildScore（Draft 验证用初始参数，非最终平衡值）

| 火焰来源 | 基础贡献 |
|---|---|
| 火焰武器 | +3 |
| 火焰符号 | +1 / 个 |
| 火焰技艺 | +2 |
| 已获得火焰构筑奖励 | +2 |

| Score | 构筑状态 | 意义 |
|---|---|---|
| 0 | 未建立 | 可提供构筑种子 |
| 1–3 | 初步倾向 | 开始出现相关奖励 |
| 4–6 | 已形成构筑 | 提供协同奖励 |
| 7+ | 成熟构筑 | 提供强化/进阶/转型机会 |

### 3.5 火焰共鸣的作用方式（禁止纯数值）

- 无火焰构筑 → 提供火焰路线**初始种子/启动机会**
- 已有火焰倾向 → **增强已有火焰机制**，产生实际协同
- 火焰构筑成熟 → 强化现有路线，而非重复给基础加成

核心是奖励"形成构筑的行为"，不是加一个计数器。

### 3.6 数据结构

```gdscript
# BuildState（RunStateAnalyzer 在生成 Draft 前统一计算）
var tags: Dictionary = {}              # tag -> float 强度
var weapon_contributions: Dictionary = {}
var symbol_contributions: Dictionary = {}
var skill_contributions: Dictionary = {}
var reward_contributions: Dictionary = {}
var build_scores: Dictionary = {}      # "fire" -> score
```

> 🔴 **修正点 D**：技艺贡献项需 P0 确认——现有 8 项技艺（坚韧/守势/备用药剂/回春/积蓄/落点吸附/宽判窗口/废铁豁免）**没有火焰标签**。首期 `skill_contributions` 对火可能为 0，除非新增火系技艺（不在本次范围）。契约记录此事实，避免 Agent 强造。

## 4. Analytics：复用现有 Telemetry，扩展事件

### 4.1 现状（源码核验）

- 载体：`scripts/systems/run_telemetry.gd`（`class_name` 未注册，`duel_controller:425` 用 `preload().new()` 注入；每局 reset，不落盘、不吃随机）。
- 现有奖励相关方法：`on_reward_shown(n:int)`（`:139`，只记分母）、`on_reward_pick(id:String)`（`:143`，只记 ID）。
- 调用点：`reward_system:1062`、`duel_controller:497/789/823/835`。

**决议：沿用 `_telemetry`，扩展事件与方法签名，不新建 Singleton。**

### 4.2 新增/扩展事件契约

| 事件方法 | 触发时机 | 必要字段 |
|---|---|---|
| `on_reward_shown` | 三选一展示时 | **扩展签名**：draft_id / room / reward_ids / hp_ratio / build_tags / gold / reward_rarities / reward_scores（debug） |
| `on_reward_selected` | 玩家选择时 | draft_id / reward_id / slot / hp / build_tags |
| `on_reward_rerolled` | 每次重抽 | draft_id / free_or_paid / cost / reroll_index |
| `on_reward_skipped` | 跳过奖励 | draft_id / reward_ids / room / hp |
| `on_reward_applied` | Resolver 成功 | reward_id / effect_id / result |
| `on_reward_apply_failed` | 执行失败 | reward_id / effect_id / reason |

- 事件名沿用 `on_*` 习惯（项目现有命名），不改造成新事件总线风格。
- `on_reward_shown(n:int)` 改为结构化参数——**这是改签名**，不是新增同名方法；调用点 `reward_system:1062` 同步改。
- `reward_scores` / 过滤原因仅在 Debug/开发环境记录，正式运行不冗余。

### 4.3 为什么必须记录 rerolled

区分：看到就选 / 三张都不满意而重转 / 免费重转后仍选回血 / 付费后选构筑 / 经常跳过。只看最终选择率会误判 Draft 质量。

### 4.4 Analytics 目标（不是每张卡选取率相同）

回答：是否总选治疗？是否形成不同构筑？是否愿为构筑放弃即时收益？免费重抽是否提升满意度？哪些卡同屏却从不被选？某卡是否只在特定阶段有价值？Draft 组合是否有明显最优解？

## 8. 实施后的设计变更记录（2026-11-18）

> 以下变更偏离附录 B.3 的原始决议（5 张种子卡），经用户确认后执行，留痕于此。

### 8.1 删除「幸运余波」种子卡（B.3 偏离）

- **原决议**：`seed_lucky_afterglow`（免费重抽）作为 5 张验证卡之一（操控类）。
- **变更**：删除该卡，种子卡从 5 张减为 4 张。
- **理由**：
  1. 免费重抽（无论三选一重抽还是战斗内转轮重转）不产生构筑价值，与 v2.0 §21「三选一是构筑决策引擎」定位不符；
  2. 战斗内转轮重转已有 3 张消耗品（重转卷轴 / 赦免令 / 重铸风暴），功能重复；
  3. 作为验证卡两头不靠：既验证不了操控手感（在战后界面），也不产生构筑深度。
- **连带清理**：Resolver 的 `free_reroll` / `grant_consumable` 分支、Composer 的免费重抽状态、
  Presentation 的对应文案、相关测试断言，均已移除。付费三选一重抽按钮保留（独立功能，不受影响）。

### 8.2 火焰共鸣卡文案修正

- **原文案**："强化火焰构筑。已有火系武器/符号/技艺时产生协同"——承诺了一个玩家感知不到的战斗收益。
- **实际效果**：`flame_affinity` 只写 `element_affinity.fire += 1`，影响后续三选一的抽卡权重（构筑导向），
  不直接产生战斗增益。
- **新文案**："本局火焰构筑 +1：让火系装备/符号/牌谱更容易在后续三选一中出现"——诚实说明是抽卡加权卡。
- **说明**：这不是削弱，而是消除"卡面承诺与实现不符"的误导。构筑导向本身符合 v2.0 设计，只是原文案表述失当。
