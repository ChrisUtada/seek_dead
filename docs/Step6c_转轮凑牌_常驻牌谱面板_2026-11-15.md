# 转轮凑牌重构 · §9.1 常驻牌谱面板（2026-11-15）

> 依据：方案 §9.1「战斗界面分为两个信息区」  
> 状态：**第一版完成**（两分区 + 组件状态 + 触发高亮）

---

## 1. 面板长什么样

屏幕左上（`(12, 96)`），半透明深色底，宽 196：

```text
武器牌谱
🔥 W01 烈焰共鸣
  燃 · 火系伤害 · 任意武器牌

技能术式
🛡 T02 防御术式
  护盾技能 · 任意武器牌 · 任意武器牌
```

- **已满足的组件**：蓝青色
- **缺的组件**：暗灰色（`#4a5563`）
- **牌谱标题色**：本回合生效 = 金色；已凑齐但没触发 = 绿色；未凑齐 = 浅灰

## 2. 数据从哪来

每回合 `_apply_patterns()` 末尾更新一次：

| 字段 | 来源 |
|---|---|
| 列哪些牌谱 | `PatternSystem.unlocked_patterns(loadout + charms)`，武器牌谱最多 2 条、技能术式 1 条 |
| 组件标签 | `PatternMatcher.describe_condition(match_rule 的每个条件)` |
| 是否满足 | `PatternMatcher.diagnose(cards, match_rule)`（新增） |
| 是否生效 | `acc["pattern_weapon"]` / `acc["pattern_skill"]` |

## 3. 新增的两个纯函数

### `PatternMatcher.diagnose(cards, rule)`

`solve_rule` 只回答「能不能凑成」，面板需要「差哪个」。诊断用贪心分配：

```gdscript
{ "done": bool, "satisfied": [0, 1], "missing": [2] }
```

只在无解时用于展示缺失项，**判定仍走 `solve_rule` 的回溯** —— 两者结果差异只影响
「高亮哪个 chip」，不会让不该触发的牌谱触发。

### `PatternMatcher.describe_condition(cond)`

把结构化条件翻成玩家能读的短标签：

| 条件 | 标签 |
|---|---|
| `{sym: burn}` | 燃（读符号的 `name`） |
| `{kind: damage, source_element: fire}` | 火系伤害 |
| `{source_kind: weapon}` | 任意武器牌 |
| `{source_kind: skill, skill_role: shield}` | 护盾技能 |

## 4. 为什么「武器牌谱最多 2 条」

单局只解锁 3–6 条，但双武器构筑通常只有 1–2 条满足解锁条件。上限 2 是为了
面板不占掉半个屏幕 —— 如果以后构筑能同时解锁更多，这个数字要跟着调。

## 5. 实现上的取舍

| 决定 | 理由 |
|---|---|
| 动态创建 PanelContainer + RichTextLabel | 不为一个面板改 `battle_hud.tscn` |
| `mouse_filter = IGNORE` | 不挡点击（它覆盖了左上区域） |
| `fit_content = true` + 固定宽 196 | 高度随内容，宽度固定避免跳动 |
| `is_inside_tree()` 守卫 | headless 测试里 UI 缺失不会崩 |
| bbcode 上色 | 一个 RichTextLabel 就够，不用为每个 chip 建节点 |

## 7. 没做的部分

| 项 | 说明 |
|---|---|
| 缺组件时给「怎么补」的提示 | 例如「缺火系伤害 → 换一把火武器」，需要构筑推荐逻辑 |
| 技能术式显示多条 | 当前只显示 1 条（方案 §9.1 也只要求「当前已携带的一条技能对应内容」） |
| 折叠 / 开关 | 面板常驻，没有让玩家收起的手段 |
| 护符修改的标记 | 方案提到「护符修改在牌谱上标记来源」，当前没有护符级签名 |
